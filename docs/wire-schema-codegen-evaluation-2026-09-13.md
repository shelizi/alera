# Wire schema/codegen and workspace.createManaged retry evaluation

Date: 2026-09-13

## 1. Batch R: wire contract schema/codegen evaluation

Decision: Keep the handwritten wire types and golden fixture tests for now. Do not introduce a shared schema/codegen pipeline in this batch. Add only low-cost shared constants and fixture assertions if a follow-up wants to reduce spelling drift without taking on a second generated-code pipeline.

### Change cost today

The current protocol is a mixed projection rather than one identical object model: the Rust host builds response envelopes and payloads, desktop projects the response into typed client models, and mobile adds its own gateway surface. The response envelope is assembled in Rust at `rust/alera-cli/src/terminal_host/protocol.rs:336-348`, while mobile method admission is separately defined at `rust/alera-cli/src/terminal_host/server/mobile_gateway_surface.rs:92-220`.

The counts below are per commit and per side, not deduplicated across a feature series. "Desktop/test" groups `lib/` with `test/` because the desktop wire consumers and their golden fixture assertions are split across those trees, as illustrated by `test/unit/terminal_host_wire_lifecycle_fixtures_test.dart:237-250`. Documentation and repository-governance files are excluded from the side counts.

In particular, the fixture and generated-output changes are often a second wave after the producer and consumer changes rather than a replacement for them.

### Drift risk and the existing fixture shield

I found no handoff entry describing a production wire-drift incident between Rust, desktop, and mobile. The handoff instead records the fixture inventory and explicitly pins non-intuitive asymmetries, including legacy subsets, unknown fields, binary framing, and retry behavior at `docs/handoff-architecture-refactor-2026-09-11.md:884-916`. The same handoff lists the real bugs caught in the broader architecture work as lost-reply re-entry, tag uniqueness, clone deduplication, and settings partial commit, rather than a cross-language wire-drift defect at `docs/handoff-architecture-refactor-2026-09-11.md:1478-1488`.

The fixture suite already tests behavior that a shape-only schema cannot establish: the Rust lifecycle fixture checks that the binary upgrade is queued behind the hello response at `rust/alera-cli/src/terminal_host/server/wire_fixture_tests_lifecycle_hello.rs:199-210`, Rust accepts an unknown request field in the lifecycle fixture at `rust/alera-cli/src/terminal_host/server/wire_fixture_tests_lifecycle.rs:400-425`, and the desktop fixture test asserts that unknown response fields are ignored at `test/unit/terminal_host_wire_lifecycle_fixtures_test.dart:237-250`. The handoff records 59 fixtures at that inventory point, including stream, lifecycle, request/error, and legacy-subset coverage at `docs/handoff-architecture-refactor-2026-09-11.md:902-915`.

That is effective drift protection for the current risk profile because the fixtures exercise the actual Rust server output and the client projections, not only independently generated serialization snapshots. It does not prove that every future method is covered, so the low-cost improvement is to require a fixture for each new public method and to centralize the most error-prone string constants.

### What codegen can cover

A shared schema could generate stable records for the common response envelope, request and response payload shapes, nullable versus required fields, and the known `errorCode` enum. It could also generate method-name and capability constants. Those are real static repetitions today: Rust hand-builds the response envelope at `rust/alera-cli/src/terminal_host/protocol.rs:336-348`, the hello response carries capability fields at `rust/alera-cli/src/terminal_host/server/client_delivery.rs:47-80`, and typed conflict details are manually named in `rust/alera-cli/src/terminal_host/server/requests/runtime_settings.rs:111-121`.

The useful boundary would be a generated shared subset, not a generated replacement for every Dart and Rust model. Fields such as `archivedAt` can be generated safely when their nullability and serialized name are stable, while operation-specific projections should remain explicit because the mobile and desktop consumers do not expose the same surface.

### What codegen cannot cover

- Binary frame upgrade and downgrade semantics are ordered protocol behavior: the host stores the per-client request, queues an upgrade marker after the hello response, and only then switches framing at `rust/alera-cli/src/terminal_host/server/client_delivery.rs:47-80` and `rust/alera-cli/src/terminal_host/client.rs:307-337`. A schema can describe `binaryFrames`, but it cannot make an implementation switch at the correct byte boundary or preserve the newline fallback.
- Capability negotiation is behavioral. The protocol defines the binary capability and enabled event at `rust/alera-cli/src/terminal_host/protocol.rs:103-110`, while mobile advertises and filters capabilities through `rust/alera-cli/src/terminal_host/server/mobile_gateway_surface.rs:36-90` and `rust/alera-cli/src/terminal_host/server/mobile_gateway_surface.rs:92-220`. Generated constants can prevent spelling mistakes, but they cannot decide which capability is granted or which downgrade path is safe.
- Unknown-field, missing-field, and legacy-subset tolerance are parser and compatibility policies. The Rust and desktop fixture cases prove that the current policy is intentionally asymmetric at `rust/alera-cli/src/terminal_host/server/wire_fixture_tests_lifecycle.rs:400-425` and `test/unit/terminal_host_wire_lifecycle_fixtures_test.dart:237-250`; generating the same strict model on both sides could make that policy less visible rather than safer.
- The mobile namespace and allowlist layer remain a routing policy. Mobile uses `mobile.*` for mobile-only verbs such as its hello path at `mobile/lib/src/features/runtime/infra/mobile_runtime_client.dart:200-220`, while generic workspace methods such as `workspace.createManaged` are admitted by the mobile allowlist at `rust/alera-cli/src/terminal_host/server/mobile_gateway_surface.rs:92-220`. A generator could emit names, but it cannot replace the policy that decides which names are reachable from mobile.
- Ordering, retry disposition, OCC semantics, setup side effects, and event publication are behavioral contracts. The OCC parser and conflict response are implemented at `rust/alera-cli/src/terminal_host/server/requests/runtime_settings_validation.rs:92-99` and `rust/alera-cli/src/terminal_host/server/requests/runtime_settings.rs:111-121`, while managed-workspace ordering is implemented at `rust/alera-cli/src/managed_workspace.rs:162-248`. A generated type cannot decide when a revision is stale or when a broadcast follows a commit.
- Desktop event filtering is also policy rather than shape. The desktop client maintains an allowlist at `lib/src/features/workbench/infra/terminal_host/terminal_host_client_models.dart:254-278` and applies it before emitting session events at `lib/src/features/workbench/infra/terminal_host/terminal_host_client_session_events.dart:62-80`.

### Adoption cost and binding risk

This repository already has two committed generated-code workflows. The agent rules require one-shot `build_runner` generation, EOF normalization, and verification of generated files at `AGENTS.md:26-33`, and they treat FRB bindings under `lib/src/rust/` as committed output regenerated through `make frb-generate` at `AGENTS.md:44-47`. The Dart modernization guide also warns that generated files are regenerated rather than manually modernized and that explicit mapped fields preserve serialization order at `docs/dart-3.13-modernization.md:5-19` and `:27-35`.

CI makes that binding visible: the pull-request workflow regenerates desktop and mobile outputs, normalizes and formats them, and fails on a diff at `.github/workflows/pr.yml:148-163`. A shared wire schema would add a third generator, its version pin and invocation, generated Rust and Dart outputs, failure modes for partial regeneration, and another source of generated-code churn. It would also need explicit rules for legacy fields, mobile projections, and serialization order rather than assuming that one generated model can replace those policies.

If this decision is revisited, the safest schema would live as a versioned protocol source under a dedicated wire-schema directory and generate only the common envelope, stable payload records, method names, capabilities, and error codes. The repository would need explicit `make` and CI targets that regenerate both language outputs and fail on a dirty diff, while handwritten adapters would retain mobile routing, compatibility parsing, frame negotiation, event filtering, retry semantics, and OCC behavior. That is a viable future design, but its adoption cost is not justified by the evidence in this batch.

### Batch R recommendation

Keep handwritten types plus golden fixtures. The recorded fixture inventory already provides cross-language drift detection at `docs/handoff-architecture-refactor-2026-09-11.md:902-915`, and the handoff does not record a real wire-drift incident in its bug inventory at `docs/handoff-architecture-refactor-2026-09-11.md:1478-1488` that would justify binding the three projections to a new generator. The follow-up hardening worth doing without a schema pipeline is to centralize method-name, capability, and error-code constants per language, require a golden fixture for every new public method, and add explicit tests for unknown fields, legacy subsets, and downgrade behavior.

## 2. workspace.createManaged retry disposition

Decision: Keep the current fail-closed retry disposition for now. Do not make a repeated `workspace.createManaged` request infer and return the first workspace until the operation has an explicit mutation identity and a completion receipt that covers the deferred job lifecycle; the current request has no mutation id at `rust/alera-cli/src/managed_workspace.rs:35-65`, and the current create dispatch does not enter the receipt flow at `rust/alera-cli/src/terminal_host/server/deferred_requests.rs:281-287` and `rust/alera-cli/src/terminal_host/server/requests/idempotency_receipts.rs:62-129`.

### Current fail-closed mechanics

The request type has an optional workspace `id`, project and branch fields, path controls, parent linkage, and setup flags, but no `clientMutationId` at `rust/alera-cli/src/managed_workspace.rs:35-65`. The server dispatch parses the request, assigns the host-owned setup-script directory, and starts the deferred creation job at `rust/alera-cli/src/terminal_host/server/deferred_requests.rs:281-287`.

Before creating a worktree, the handler rejects an existing requested id at `rust/alera-cli/src/managed_workspace.rs:98-107`, rejects an existing branch at `rust/alera-cli/src/managed_workspace.rs:139-145`, and rejects a path already represented by a workspace at `rust/alera-cli/src/managed_workspace.rs:147-160`. These are the duplicate checks that make a complete first attempt fail closed on an identical retry.

Those duplicate errors use the generic state-error path: `json_result` maps the failed result to `HostError::state` at `rust/alera-cli/src/terminal_host/server/request_payloads.rs:5-20`, and only `HostError::Conflict` adds `errorCode` and `errorDetails` at `rust/alera-cli/src/terminal_host/host_error.rs:41-55`. The resulting duplicate response is therefore the normal error envelope with the request id, `ok: false`, and the error string, without a typed duplicate error code; the envelope shape is defined at `rust/alera-cli/src/terminal_host/protocol.rs:336-348`. The separate deferred-admission overload path is typed as `deferred_request_backpressure` at `rust/alera-cli/src/terminal_host/server/deferred_admission.rs:197-223`, but that is a busy-host rejection, not the duplicate-after-success case.

The deferred job reports success only after `create_managed_workspace` completes and broadcasts `workspacesChanged`; failure writes an error response at `rust/alera-cli/src/terminal_host/server/managed_workspace_requests.rs:131-159` and `rust/alera-cli/src/terminal_host/server/managed_workspace_requests.rs:179-196`. There is no receipt preparation in the create dispatch, while the existing receipt flow is explicitly used by `terminal.terminate` at `rust/alera-cli/src/terminal_host/server/requests.rs:390-470`.

### What the first creation leaves behind

Creation is non-atomic across filesystem, Git, database, relation, and setup work. The handler creates the parent directory and Git worktree before building the `Workspace` row at `rust/alera-cli/src/managed_workspace.rs:162-188`. The Git helper checks path occupancy, creates or reuses the branch, sets upstream when needed, and creates the worktree, with branch cleanup only for some failures, at `rust/alera-core/src/git.rs:126-204`.

The workspace row is then upserted and committed through `RuntimeStore` at `rust/alera-cli/src/managed_workspace.rs:185-212` and `rust/alera-core/src/runtime/store.rs:836-878`; the persisted schema includes the workspace identity, project, branch, path, lifecycle fields, and `archivedAt` at `rust/alera-core/src/runtime/runtime_schema.rs:27-45`. If a parent was requested, linking happens after the row write and validates both workspaces before inserting the relation at `rust/alera-cli/src/managed_workspace.rs:213-220` and `rust/alera-core/src/runtime/store.rs:1223-1298`. A link failure can therefore leave the workspace row and worktree behind even though the request returns an error.

Setup is later in the sequence. Inline setup runs against the existing workspace and returns a report at `rust/alera-cli/src/managed_workspace.rs:222-248` and `rust/alera-cli/src/worktree_setup.rs:88-125`; deferred setup may write a setup script after the workspace exists at `rust/alera-cli/src/worktree_setup.rs:34-70`. These steps do not form one database transaction with the Git worktree or the workspace row.

For a complete first attempt with an explicit id, an identical retry normally stops at the existing-id check before touching the filesystem again. For a first attempt that reached the database, the branch or path checks can stop it instead. For a partial attempt that created Git state before the row was committed, the retry can instead reach the Git helper's occupied-path or branch rules. The code has no single durable operation record that tells the retry whether the existing state is the successful result, a failed partial attempt, or a workspace that still needs setup; the request shape and dispatch path have no mutation receipt at `rust/alera-cli/src/managed_workspace.rs:35-65` and `rust/alera-cli/src/terminal_host/server/deferred_requests.rs:281-287`, while the individual stages above are the evidence for that limitation.

### Existing receipt machinery

The repository already has a general receipt table keyed by operation, caller scope, and `clientMutationId`, with a payload digest, state, result JSON, and timestamps at `rust/alera-cli/src/terminal_host/server/requests/idempotency_receipts.rs:9-23`. Receipt preparation rejects a reused id with a different payload, replays a settled result, reports an in-progress operation, and inserts the first pending record at `rust/alera-cli/src/terminal_host/server/requests/idempotency_receipts.rs:62-129`; settlement stores the final result at `rust/alera-cli/src/terminal_host/server/requests/idempotency_receipts.rs:185-233`.

That machinery makes a future idempotent create possible, but it is not a trivial switch for this handler. The client would need to send and preserve a stable mutation id across a timeout, the server would need to prepare the receipt before admitting the deferred job, and the completion path would need to settle the receipt with the exact workspace creation result or remove it according to an explicit partial-failure policy. A receipt lookup can avoid new workspace columns, but it does require new receipt rows and lookups for this operation and a decision for pending jobs after host restart.

### Wire, database, and UI impact of the recommendation

Wire impact under the recommendation is zero: retain the current request fields and generic duplicate state-error payload. The desktop client sends the managed-create fields without a mutation id at `lib/src/features/workbench/infra/runtime_managed_workspace_client.dart:45-75`, and mobile does the same at `mobile/lib/src/features/runtime/infra/mobile_runtime_workspace_client.dart:96-120`.

Database impact under the recommendation is zero: do not add workspace columns, receipt rows, or reconciliation records. The existing workspace table and current staged writes remain the source of the observed partial state, as shown by the upsert and relation sequence at `rust/alera-cli/src/managed_workspace.rs:185-220`.

UI impact under the recommendation is zero: preserve the current generic error mapping and collision handling. Desktop maps an untyped host error to `StateError` and typed conflicts separately at `lib/src/features/workbench/infra/terminal_host/terminal_host_client_requests.dart:119-135`, while mobile does the corresponding mapping at `mobile/lib/src/features/runtime/infra/mobile_runtime_client.dart:423-442`. The desktop prompt flow recognizes collision text and offers an alternate retry at `lib/src/features/workbench/presentation/prompt_workspace_dialog.dart:271-285` and `:315-333`; mobile uses the same collision-oriented prompt behavior at `mobile/lib/src/features/workbench/application/prompt_workspace_controller.dart:169-205` and `:352-355`, while its ordinary list flow retains parent-link failures at `mobile/lib/src/features/workbench/application/workspace_list_controller.dart:190-230`.

If the product later changes to return the first workspace, the wire change should be additive: accept an optional `clientMutationId` and define replay, in-progress, payload-mismatch, and partial-failure responses. The database change need not add workspace columns if the existing receipt table is extended by operation usage, but it must persist receipt state and result JSON. The UI change would require both clients to preserve the mutation id across timeout retries and treat a replayed workspace result as success instead of interpreting the duplicate text as a request to choose a new identity. None of those changes is present in the current create clients or dispatch path cited above.

### Paste-ready contract paragraph

```text
`workspace.createManaged` is fail-closed on retry. A client that times out or loses the connection must treat the outcome as unknown and must not expect repeating the identical request to return the workspace created by the first attempt. The host re-validates the requested workspace id, branch, and path, and returns the existing duplicate state error when one of those values was persisted (`rust/alera-cli/src/managed_workspace.rs:98-160`). Partial filesystem or Git state, or a persisted workspace whose later relation or setup step failed, may remain and must be reconciled through normal workspace listing or cleanup rather than silently treated as a new successful create (`rust/alera-cli/src/managed_workspace.rs:162-248`). Clients may retry with a newly generated identity only when the product flow explicitly chooses a new workspace identity.
```
