# Terminal operation contract

This table answers the eight transaction/replay questions from the architecture refactor handoff (section 13) for the terminal surface handled by `ServerActor`: `createOrAttach`, `write`, `resize`, `terminal.read`, `setOutputPaused`, `detach`, `terminate`, `terminal.create`, `terminal.attach`, `terminal.restart`, `terminal.reclaim`, `terminal.driver.list`, `terminal.runningProcesses`, and `terminal.pulse.*`. Companion to `orchestration-operation-contract.md`, `project-operation-contract.md`, `workspace-operation-contract.md`, and `tab-layout-operation-contract.md`; update the table and its pinning tests together.

Authority splits three ways, and the split is the point of this document:

- Persisted workspace and tab records live in `RuntimeStore`. A `kind = "terminal"` tab row owns the public session handle through `payload.terminalSessionId` and carries `spawnOnCreate`, `terminalPulse`, and launch metadata; the row survives host restarts.
- Terminal history lives in `TerminalHostHistoryStore`: one `checkpoints` row per session plus sequenced `outputChunks` rows. It is the only scrollback that survives a host restart.
- Live PTY state lives in `ServerActor.sessions` and nowhere else: PTY handles, the bounded input queue (64 writes), the scrollback ring, attached client ids, per-client delivery cursors, current dims, the `SessionDriver` seat, and the session instance id are all in memory. A `sessionId` absent from `sessions` fails `require_session` with `Terminal session is not attached: {id}`; a session-scoped request never rebuilds the map from persisted state. Only `createOrAttach`, `terminal.attach`, and `terminal.restart` mint or remint a PTY.

Keyed `terminal.terminate` requests use the `terminalHostIdempotencyReceipts` table in `RuntimeStore`'s SQLite database. The receipt is scoped by operation, authenticated caller scope, and `clientMutationId`; it stores a SHA-256 payload digest and the result. A receipt is reserved as pending before teardown and settled only after successful teardown. A retry while it is pending returns `clientMutationId is already in progress.` Receipts persist across host restarts for seven days. Expiration is lazy: each keyed receipt reservation deletes rows older than seven days, then trims the oldest rows above 256 per operation and caller scope or 4096 globally. A failed termination removes its newly-created receipt. A missing `clientMutationId` does not touch receipt storage and keeps the legacy path.

View and attachment state is per client and ephemeral: `output_paused_clients`, `output_resync_pending_clients`, and `delivered_output_cursors` live on the session, and `dispose_client` detaches a disconnected client from every session without touching the PTY.

## T2-D6: transferred Desktop Tab close is receipt-bound (2026-10-30)

An explicit Workbench Tab close uses the **Tab record captured by the closing view**, including the original observed `lastTerminalTabTransfer.id`, and sends both `expectedWorkspaceId` and `expectedTransferMutationId` to Host `tab.remove`. The same snapshot and receipt are reused for a request timeout/disconnect retry. A serialized `tab.remove` for *any previously transferred Terminal* **rejects a missing receipt**, not only a mismatched supplied receipt. This blocks stale Desktop A→B→A removal while preserving old behavior for never-transferred Tabs. Legacy repositories that cannot carry an observed receipt fail closed on moved terminals. The earlier D5+ optional-receipt wording is superseded.

The new Store exact-pane-prune guard and local Journal exclusive file claim do **not** make active PTY ownership a cross-process lease: Host restart, pending attach/detach/close and crash between SQLite commit and Session reparenting still need defined conservative recovery. The Host advertises `tab.transfer.capabilities.supported=false` throughout D6; no Flutter/Cargo compilation, regression tests, platform E2E, push or release were performed.

## T2-D5+: moved PTY multi-client termination and Mobile observed owner (2026-10-30)

For a Terminal with a persisted `lastTerminalTabTransfer` receipt, `terminate` still requires current `expectedWorkspaceId`, `expectedTabId`, and latest **observed** `expectedTransferMutationId`. D5+ also rejects an explicit termination if any other Host client remains in `Session.clients`; the old window must first detach the other view. `tab.remove` is additionally preflighted **on the Actor before its queued background deletion**, rejecting a transferred live Session with multiple attached clients. The source record is not removed on this refusal.

The updated Mobile client uses `MobileObservedTerminalTermination` and `MobileObservedTabRemoval` only when supported, sending the Workspace/Tab/last receipt from its **original observed** `WorkspaceTabSummary`. A stale transferred Terminal close error is not swallowed and followed by `tab.remove`; the Agent Terminal action likewise confirms the Tab still appears in the selected Workspace. Old mobile clients lacking the new scoped methods are safely unable to close moved Terminals.

These are **fail-closed checks on the current Host Actor's attached-client set**, not a durable cross-process Session lease or authoritative last-window reference count. Pending/queued attach/close, Host crash, or a PTY already missing after commit still need recovery rules and Windows/macOS multi-process validation. `tab.transfer.capabilities.supported=false` remains unchanged. This batch was only formatted and Git-diff checked; no tests, analyzer, build or release were run.

## T2-D5: remote Tab retirement is not Session exit (2026-10-30)

Workbench's watcher-driven cleanup only releases old local view/editor resources. A moved Terminal disappears from its **source** Workspace's Tab list without terminating its PTY or its Claude/Codex process. `WorkbenchRetiredResourceCleaner` must therefore **not** clear its Codex transcript watcher merely because an observer lost the source Tab: callers may opt into `confirmedSessionExit:true` only with independent evidence that the Session really exited. Explicit local Terminal Close retains its separate lifecycle cleaner. Final remote-exit watcher reclamation still needs owner-aware confirmation; this change is not a global cross-process last-view lease.

The Host continues reporting `tab.transfer.capabilities.supported=false`; D5 has only formatting and Git diff checks, not Flutter/Cargo compilation, platform E2E or release verification.

## T2-D4: explicit termination requires the last observed transfer revision (2026-10-30)

For a Terminal Tab carrying `payload.lastTerminalTabTransfer.id`, Host `verify_terminal_termination_owner` compares the request's `expectedWorkspaceId`, `expectedTabId` **and** `expectedTransferMutationId` against the currently owned Session and the **last** persisted transfer receipt. This closes the A→B→A ABA hole: an old window that originally observed Workspace A cannot terminate the moved-back PTY just because its Workspace/Tab identity happens to match again. The current Desktop terminal view captures the receipt from the actual `WorkspaceTabRecord` observed on creation or sync, and passes that value with `terminate`; it must never query the Host's newest receipt just before closing. Old clients without this field **fail closed** for moved Tabs, including current Mobile terminate callers; unmoved legacy Tabs continue to work without a receipt.

`detach` is a per-client view/cursor release and does **not** terminate the Host PTY. Unknown `tab.transfer` replies are explicitly reported as unknown with a read-only `Check status` UI action; only receipt + live PTY confirmation and authoritative **two-Layout** readback let the client release its local guard. Global cross-process Session lease and Host crash partial-commit recovery are still open. **Capability remains OFF**, and no Cargo/Flutter tests, Analyzer, builds or Windows/macOS E2E were run for D4.

Every operation runs on the actor mailbox. `write` and `terminal.pulse.configure` enter through the deferred-request path (`deferred_requests.rs`), and the runtime-mutation barrier rejects `createOrAttach`, `write`, `terminate`, `terminal.create`, `terminal.attach`, `terminal.restart`, and `terminal.pulse.configure` while a mutation is outstanding; `terminal.read`, `resize`, `setOutputPaused`, `detach`, `terminal.reclaim`, `terminal.driver.list`, `terminal.runningProcesses`, and `terminal.pulse.status` stay available. `HostError::State` messages go to the wire verbatim (clients pattern-match some of them), `HostError::Format` lands as `FormatException: ...`, and `HostError::Conflict` adds `errorCode`/`errorDetails`. Mobile clients are restricted to an allowlist: `terminal.create`, `terminal.attach`, `terminal.restart`, `terminal.driver.list`, `write`, `resize`, `setOutputPaused`, `detach`, and `terminate`.

## T2-D3: transferred live Terminal ownership and safe restart (2026-10-30)

**Status: implemented in the isolated integration branch, not tested and not enabled.** Host `tab.transfer.capabilities.supported=false` is intentionally retained; cross-workspace Drop is not a supported user action yet. The legacy rows below predate Terminal transfers; for a tab containing `payload.lastTerminalTabTransfer`, the following narrower rules override their old generic statements:

- **Live PTY identity:** The Host checks `sessionId`, current display `workspaceId`, and `tabId` on `createOrAttach` and `terminal.restart`. A stale window cannot attach, restart, or terminate a moved terminal by using its former workspace identity. The desktop `terminate` request sends the old view's expected workspace/tab; the Host rejects an incorrect expected owner, instead of treating it as permission to kill a shared PTY. `detach` only releases that client's view/cursor and does not terminate the PTY.
- **Existing PTY reattachment:** If a moved live Session still exists, attaching preserves the process, output cursor and scrollback; the original launch folder may have since disappeared and is **not** revalidated for a read-only attachment.
- **Process creation after a move:** When an absent/dead Session must be reminted by `createOrAttach`, or an explicit `terminal.restart` is requested, the Host verifies that `terminalExecutionWorkingDirectory` exists and its canonical path matches the requested launch directory. Failure is reported **before** terminating a still-running PTY or starting a new shell. Do not substitute the destination project's path. The client also checks the launch directory before sending an explicit restart.
- **Host startup and spawn-on-create:** Previously moved terminals use the original launch path for `default_terminal_launch`, not the display workspace's checkout. If that path is unavailable, Host startup logs an error and **retains the transferred Tab row** for recovery rather than deleting it along with its ownership. The saved execution path means the *launch directory*, not necessarily the Shell's current CWD after a user typed `cd`.
- **Unknown transfer outcome:** A timeout/disconnect never means the transfer failed. The client queries `tab.transfer.status` with the *same* mutation ID and live PTY identity, and if unprovable, retains the unknown operation so a second move of that Tab cannot mint a fresh ID. When the Host confirms the original receipt, refresh the two authoritative Workspace layouts before the user tries again.

These are functional source-code constraints only; D3 did not run Cargo/Flutter tests, analyzer, builds or multi-process/macOS/Windows E2E. **Global cross-process Session leases and last-view ownership are not yet verified.**

## Internal machinery

These are not requests, but the matrix columns above rely on them.

| Mechanism | Contract |
|---|---|
| PTY output | `handle_pty_output` appends to the scrollback and arms two independent batch tracks: `output_batch` (8 ms debounce or 64 KiB early flush) for client delivery and `durable_output_batch` (100 ms or 64 KiB) for `outputChunks` persistence, plus the debounced checkpoint timer |
| Output delivery | `flush_output_batch` pushes one `ClientFrame::Output` per attached, non-paused client on the bounded terminal lane (8 frames local, 32 mobile). Only an accepted frame advances that client's delivery cursor. A `Full` lane marks the client paused + resync-pending and arms a resync timer; a `Closed` lane schedules disconnect |
| `OutputResyncTick` | Emits `outputResyncRequired` on the terminal lane while the flag is pending; `Full` reschedules, `Closed` clears the flag and schedules disconnect. The client answers with `setOutputPaused` false, and a restart-resynced client always lands on the snapshot path because `attach_for_resync` dropped its cursor |
| Durable output | `persist_output_batch` runs `append_output(sessionId, sequence, data)` off the actor loop, tracked in `pending_output_writes` for the `await_output_writes` barrier (2 s). `append_output` only inserts while a `checkpoints` row exists, which is why `Session::start` writes its checkpoint before the session is reachable |
| Checkpoints | `CheckpointTick` (5 s debounce), `immediate_checkpoint` (detach, kept-on-exit, disconnect, dispose), and `handle_checkpoint_tick` all flush durable output, await pending writes, `write_checkpoint`, then `trim_session(scrollback_bytes)`. `terminate(false)` writes a final checkpoint; `terminate(true)` deletes checkpoint + chunks |
| PTY exit | `handle_session_exit` disarms the pulse, queues the exit push, cleans orchestration state; `Session::handle_exit` returns `None` on an already-exited session so a second event is a no-op. A kept failed setup or failed owned spawn gets `immediate_checkpoint`; otherwise `remove_terminal_session_tab` retires tab + session + history. When the tab row is already gone the session stays in the map not-running with a final checkpoint, and a later attach remints it |
| Client disconnect | `dispose_client` drops the client's orchestration waiters, cancels its queued runtime mutations, releases its mobile driver claims (restoring `desktop_dims`), cancels prompt uploads, detaches it from every session (forgetting delivery cursors), `immediate_checkpoint`s each session, then re-arms idle shutdown. The PTY survives: no client disconnect kills a session |
| Idle shutdown | `schedule_shutdown_if_idle` arms `empty_shutdown_delay_seconds` (30 s) when nothing runs and `detached_session_shutdown_delay_seconds` (3600 s) while sessions run; persistent mode, authenticated clients, jobs, mutations, the mobile gateway, coordinators, push subscriptions, and automations all cancel it. `handle_shutdown_tick` is generation-guarded: a stale tick is ignored, and a current tick runs `dispose()`, which terminates every session with `remove_history = false` so the final checkpoint and chunks survive for the next host start |
| `host.shutdown` / `host.restart` | Non-forced calls fail while agents, sessions, jobs, or push subscriptions are active; the reply is written before disposal through the ordered `ShutdownRuntimeAfterWrite`/`RestartRuntimeAfterWrite` markers. Mobile clients cannot call `host.shutdown` |
| Startup recovery | `reconcile_spawn_on_create_tabs` walks every workspace's tabs; a `kind = "terminal"` tab with `payload.spawnOnCreate == true` re-arms after-ready prompts, requires an `Active` workspace, and respawns through `take_terminal_restart_state` + `start_new_terminal_session` at 80x24. A failed restore removes the tab row. Tabs without `spawnOnCreate` are not respawned; their PTY appears on the next attach. `upsert_workspace_tab_and_spawn` rolls back the tab row and terminates its sessions when a spawn fails |
| Startup input | `TerminalStartupInput`, `TerminalStartupSubmit`, and `OrchestrationDeferredEnter` carry the session instance id captured at schedule time; the handler drops the write when the session's instance id no longer matches or it stopped running |
| `Session::restore_exited` | Rebuilds a not-running session from `checkpoints` + `outputChunks` ordered by `(sequence, id)`, resuming `output_stream_bytes` at the persisted absolute position. A checkpoint without `ended_at` restores as interrupted with exit code -1 |

## Known gaps

- `createOrAttach` and `terminal.attach` never re-validate `workspaceId`/`tabId`/`workingDirectory`/`launch` against a live session; only `terminal.restart` checks metadata. A caller holding a stale but valid handle attaches to whatever PTY the handle names.
- `write` has no op id. Accept this for now: the client never retries writes, so a lost reply implies connection loss and reattach rather than a resend; deduplication by content is unsafe for a keystroke stream.
- `terminal_input_backpressure` is a typed `Conflict` code used by the orchestration Enter and Terminal Pulse retry paths; its wire message keeps the `terminal_input_backpressure: ...` prefix for older clients and compatibility matching.
- On the dead-handle path of `createOrAttach`, `take_terminal_restart_state` drops the old session (history preserved) before `launch` is validated, so a malformed launch still consumes the old PTY; the next call restores from the checkpoint.
- An exited session whose tab row was already removed stays in `sessions` as a not-running entry until an attach remints it or the host shuts down; `terminal.read` still serves its retained ring and `write` fails `not running`.
- Terminal Pulse configuration is persisted on the tab, but the armed rule is in memory: after a host restart `armed` reads false until the next `terminal.pulse.configure`.
