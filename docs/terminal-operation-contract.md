# Terminal operation contract

This table answers the eight transaction/replay questions from the architecture refactor handoff (section 13) for the terminal surface handled by `ServerActor`: `createOrAttach`, `write`, `resize`, `terminal.read`, `setOutputPaused`, `detach`, `terminate`, `terminal.create`, `terminal.attach`, `terminal.restart`, `terminal.reclaim`, `terminal.driver.list`, `terminal.runningProcesses`, and `terminal.pulse.*`. Companion to `orchestration-operation-contract.md`, `project-operation-contract.md`, `workspace-operation-contract.md`, and `tab-layout-operation-contract.md`; update the table and its pinning tests together.

Authority splits three ways, and the split is the point of this document:

- Persisted workspace and tab records live in `RuntimeStore`. A `kind = "terminal"` tab row owns the public session handle through `payload.terminalSessionId` and carries `spawnOnCreate`, `terminalPulse`, and launch metadata; the row survives host restarts.
- Terminal history lives in `TerminalHostHistoryStore`: one `checkpoints` row per session plus sequenced `outputChunks` rows. It is the only scrollback that survives a host restart.
- Live PTY state lives in `ServerActor.sessions` and nowhere else: PTY handles, the bounded input queue (64 writes), the scrollback ring, attached client ids, per-client delivery cursors, current dims, the `SessionDriver` seat, and the session instance id are all in memory. A `sessionId` absent from `sessions` fails `require_session` with `Terminal session is not attached: {id}`; a session-scoped request never rebuilds the map from persisted state. Only `createOrAttach`, `terminal.attach`, and `terminal.restart` mint or remint a PTY.

Keyed `terminal.terminate` requests use the `terminalHostIdempotencyReceipts` table in `RuntimeStore`'s SQLite database. The receipt is scoped by operation, authenticated caller scope, and `clientMutationId`; it stores a SHA-256 payload digest and the result. A receipt is reserved as pending before teardown and settled only after successful teardown. A retry while it is pending returns `clientMutationId is already in progress.` Receipts persist across host restarts for seven days. Expiration is lazy: each keyed receipt reservation deletes rows older than seven days, then trims the oldest rows above 256 per operation and caller scope or 4096 globally. A failed termination removes its newly-created receipt. A missing `clientMutationId` does not touch receipt storage and keeps the legacy path.

View and attachment state is per client and ephemeral: `output_paused_clients`, `output_resync_pending_clients`, and `delivered_output_cursors` live on the session, and `dispose_client` detaches a disconnected client from every session without touching the PTY.

## T2-D17: protect transferred Tab provenance at the generic SQLite Upsert boundary (2026-10-30)

**The generic RuntimeStore upsert is now part of the safety boundary.** An ordinary `tab.upsert` Host RPC is not the only way a persisted Tab can be rewritten: automation and other internal code call `RuntimeStore.upsert_workspace_tab` directly. D17 performs the existing-record read, evidence check and `INSERT ... ON CONFLICT UPDATE` **inside one SQLite transaction**, not separate reads that can overwrite each other. If the existing Tab contains a `lastTerminalTabTransfer` **or** `lastTerminalTabExit` key, even with a JSON null/malformed value, its `kind`, `workspaceId`, both evidence markers, `terminalSessionId`, original execution Workspace and original launch Working Directory are immutable via this generic API. New or previously never-transferred Tabs cannot fabricate Host-owned Transfer/Exit markers here. Ordinary Title/metadata and never-moved Upsert may proceed when the exact Host-owned fields are preserved. Valid original Transfer and PTY Exit still use their dedicated Store transactions. **This is not a full SQLite global immutable schema or a defense against every separate direct SQL/delete entrypoint**.

**Phone Close must belong to the current Host socket Client, not merely the logical View ID.** D16 retained original `viewLeaseId` and attachment revision across client recovery. D17 further makes `TerminalSessionController.attachedViewLeaseId` read the current `terminalClientProvider(hostId)` synchronously and require it to be an `AsyncData` holding the **same Client object** bound to the ready Terminal Session. A newly published Host Connection Provider invalidates the previous Controller's Close permission immediately, even if the Recovery listener has not yet switched `state` away from the old ready Session. No new View is minted and no background connection is opened to authorize a close. This still cannot prove native process/window, multi-phone, multi-App or Host-restart global ownership.

**Journal human-review cross-reference is local evidence only.** The combined Manual Recovery Dossier now associates each readable Pending Tab/mutation with well-formed, SHA256-matched resolved Archives of the same Tab, separating the *same* mutation from earlier/different ones. It also surfaces Archives that have no readable same-mutation Pending in the **non-atomic** local scan; these may be legitimate old resolutions, not necessarily lost or suspicious Host transfers. Unreadable records remain in the original inventory. `requiresHostVerification` stays true, `permitsAutomaticUnlock` false; no PID-age assumption, Host decision, mutation, lock deletion or release UX was added.

**Feature and verification:** `tab.transfer.capabilities.supported=false` remains. Only `rustfmt --edition 2021`, `dart format` and Git whitespace checks; **no Cargo/Flutter tests, analyzer, check/build, Windows/macOS/Phone E2E, Push or Release**. D18 remains responsible for durable physical Last-view ownership, Host Crash definite recovery and authorized CAS exited-Tab retirement, Store-specific Remove guard and safe human stale-lock operation.

## Historical T2-D16: safe Store replay, exact original Exit/layout inspection, click-bound mobile View (2026-10-30)

**Store-side idempotent replay is not just a matching mutation ID.** `RuntimeStore.transfer_terminal_tab_storage` rejects a preexisting `lastTerminalTabExit` key even when it is JSON null, malformed prior transfer metadata, an original PTY instance mismatch, or a prior receipt whose `to` no longer matches the current Workspace. When a lost-reply request replays the *same* mutation, it requires that **both persisted source/target Layout JSONs equal the submitted post-transfer Layouts and both complete authoritative WorkspaceTab registries match those Layouts in a single SQLite transaction**. `record_transferred_terminal_exit` also checks **presence of the Host-owned exit key**, not just non-null value, before persisting an Exit. Invalid evidence must remain intact for investigation and must not be silently replaced by a new PTY or receipt.

**A read-only exited-PTY preflight is not a delete capability.** `RuntimeStore.inspect_transferred_terminal_retirement_evidence` shares the normal transfer-status Store read transaction, validating latest receipt identity, original Session and PTY token, the Host-observed normal Exit's exact mutation/Session/Workspace/PTY Token/Code plus parseable UTC time, both persisted split/pane Layouts and all WorkspaceTab membership. It returns an optional **same-snapshot** Tab for diagnosis only. Host `tab.transfer.status` exposes `originalExitAndLayoutsConsistent` for `pty_exit_observed`, but always returns `applied:false,recoveryRequired:true`, preserving `hostGenerationMismatch` when relevant. Even a `true` field is **not proof of no other live OS process/window/device, user intent or exclusive final view**, and never authorizes delete, unlock, Journal clearing or restoring the vanished original PTY.

**A phone View ID is not its attachment generation.** `TerminalSessionController` retains the original cryptographically random `viewLeaseId` across Socket changes, but increments `_attachmentRevision` whenever a new Session is bound. The read-only `observedAttachedView` returns the original ready `(viewLeaseId, revision)` without opening a new connection. Phone transferred-Tab Close captures that original Controller/snapshot before any `await`, and after resolving the WorkspaceClient demands the **same mounted Provider, same Controller instance, same attached revision and view ID**. If it reconnected while waiting, Close must be explicitly retried by the user from the new visible state. This protects click-to-request preparation, **not** all post-RPC socket races or global Last-view ownership. Legacy removal fallback also rejects Exit-only evidence.

**Journal operator Dossier:** `inspectManualRecoveryDossier()` combines complete Pending/Lock and Resolved/Orphan local inventories, and reports UTC scan time plus unresolved/unsafe local evidence. The two directory observations are **not atomic**; root errors propagate rather than yielding a misleading partial empty list. `requiresHostVerification` is always true; `permitsAutomaticUnlock` is always false. No PID, timestamp, local archive or missing Lock is allowed to infer Host authorization.

**Gate and validation:** `tab.transfer.capabilities.supported=false`, no cross-project drag/release. D16 ran only Rust/Dart format, Git whitespace checks and isolated source commit/cherry-pick; **no Cargo/Flutter tests, analyzer, check/build, real Windows/macOS/Phone E2E, Push or Release**. D17 remains responsible for authenticated/transactional exited-Tab retirement, cross-process durable View Lease, Host crash resolution and manual stale-lock UX.

## Historical T2-D15: malformed transferred evidence is never legacy Terminal state (2026-10-30)

**Both persisted markers are protected:** `lastTerminalTabTransfer` is the exact original transfer revision/PTY identity and `lastTerminalTabExit` is only a genuine Host-observed original PTY Exit record, not a permission to destroy the Tab. `has_transfer_recovery_evidence` checks **key presence**, including an explicit null or malformed value, for **either** marker. `invalid_transfer_receipt_marker` rejects a missing Transfer paired with an Exit, wrong Tab kind, absent/blank transfer mutation/from/to/PTY instance, and an Exit record whose mutation ID, original PTY token, Workspace, Session or Exit Code does not match the transfer. No corrupted/exit-only record is ever treated as a never-transferred Terminal.

**Host paths fenced:** `verify_terminal_termination_owner`, `verify_terminal_attachment_owner` (including automatic restart), another `tab.transfer`, `tab.transfer.status` (`applied:false,recoveryRequired:true,reason:malformed_transfer_receipt`), `tab.remove` before/after background mutation, generic natural Exit cleanup and implicit Workspace/Project removal all preserve that unresolved evidence. Even a malformed receipt or an orphaned Exit marker must not authorize unscoped Detach or silent cleanup. The previous rules still require an exact original live View Token and original PTY instance for an ordinary valid transferred-Tab Close; D15 adds **no destructive retirement API**.

**Old desktop `tab.upsert` protection:** a transferred Tab's `workspaceId` and `kind` cannot change through the legacy Upsert route, and an existing malformed original receipt causes rejection instead of overwrite. A client cannot add `lastTerminalTabTransfer` or `lastTerminalTabExit` to a never-transferred or newly created Tab. `tab_compatibility` explicitly preserves existing `lastTerminalTabExit` and `terminalSessionId` as Host-owned fields, along with the transfer receipt and execution provenance. These are request-path protections; there remains no global durable multi-Host CAS for future external Store writes.

**Mobile close:** a Mobile `WorkspaceTabSummary` recognizes both persisted marker Keys, validates the original receipt and any Exit linkage, and rejects malformed/exit-only evidence before an asynchronous close. For valid transferred Tabs it still requires the previously attached phone View Lease and the original observed receipt, then uses the guarded Host `tab.remove` directly. `terminateObservedTerminal` and ordinary `removeObservedTab` refuse transferred evidence, including corrupt markers; they no longer offer a terminate-first fallback. Legacy never-transferred close stays unchanged.

**Journal archive evidence:** `inspectResolutionArchiveInventory()` lists ordinary/corrupt/orphan local files under `terminal_transfer_resolved_v1`, verifies the local Archive resolution schema and SHA256 filename against original `[tabId,clientMutationId]`. The returned `requiresHostVerification` is always true: a locally well-formed resolution marker is not a Host-signed decision, nor a permit to remove a pending plan or a stale lock. The method never follows links, deletes data or calls Host mutations.

**Validation and Gate:** `tab.transfer.capabilities.supported=false` throughout D15. Only Rust/Dart format and Git whitespace checks; no Cargo/Flutter Tests, Cargo check, Flutter analyzer/build, Windows/macOS/Phone E2E, Push or Release. D16 still needs Host-authorized original Exit retirement, durable multi-process/per-device Last-view, crash repair and Journal stale Lock manual procedure.

## Historical T2-D14: Host process generation, same-SQLite verified reply, named Mobile reconnect (2026-10-30)

The original Host transfer `ptyInstanceToken` already encodes a process-random UUID and the specific Session instance counter. **Do not mint a replacement token to recover a lost PTY.** `tab.transfer.status` now parses an exact stored receipt from/to/mutation and compares its UUID generation to this responding Host's epoch. A different, parseable generation returns `applied:false,recoveryRequired:true,reason:host_generation_mismatch`; this Host does **not** possess proof of ownership. Crucially, it does **not** prove the original Host has died (another process may be live), that SQLite transfer failed, or that the client can roll back. An exact original `lastTerminalTabExit` observation remains the stronger `pty_exit_observed` diagnostic with `hostGenerationMismatch:true`, still requiring manual reconciliation.

The D13 dual-layout store check is read-only and now returns `Option<WorkspaceTabRecord>`, not only a boolean. The Host responds to `tab.transfer.status` with the **Tab from the same SQLite transaction** that verified original Session/receipt/instance, both Workbench Layouts and all WorkspaceTab memberships. It does not use a separate Tab object read before that verification, which could have been changed by another app process. It is still not an atomic proof tying this DB read to live OS PTY state or to future writes by other Host processes.

Mobile `TerminalSessionController` reconnects using the **same already-bound random View ID**. First it attempts the new Host client normally; if the old client has already disconnected, Host ownership is freed and the new attach works without contacting a dead socket. Only when Host explicitly replies that this exact View ID is currently registered on **another Host Client**, and both clients advertised the named-view capability, the controller sends `detachTerminalWithViewLease` via its prior socket for that exact session, waits for acknowledgement, clears the old local binding, and tries the new named attach once. A lost detach reply, unreachable old client or second conflict is unresolved and **never permits reassignment or silent new View ID**. This narrows a normal reconnect gap; it is not persistent multi-device/Host-restart View authority.

Journal `remember`/`forget`/Lock release check that the Pending/Resolved roots are actual directories and evidence files ordinary files before doing I/O; inspect uses `FileSystemEntity.type(..., followLinks:false)` and refuses to dereference links. An owned lock must still have the exact original Tab SHA256, nonce, PID and version before normal deletion. These are conservative type/identity checks, **not** an adversarial race-free cross-process lock, a Host-verified recovery outcome or safe permission to unlock a crashed writer.

**Feature remains OFF and unvalidated:** `tab.transfer.capabilities.supported=false`. Only `rustfmt`, `dart format` and Git whitespace checks in D14; no Cargo/Flutter test/analyzer/check/build, physical Windows/macOS/Phone E2E, Push or Release. D15 still needs durable multi-App/Device Last-view, Host Crash outcome and authorized proof-bound exited Tab retirement.

## Historical T2-D13: dual Layout proof, Host-negotiated Mobile lease and detached-window guard (2026-10-30)

**Transfer Status must include the complete persisted display ownership.** A live PTY token plus an exact latest transferred receipt did not prove that the original source pane had dropped the Tab or that the destination (and other Tabs) were still present. The Host now calls the new read-only `RuntimeStore.verify_terminal_transfer_layout_and_receipt` **after** its live original-session check. This routine reads the Tab's exact current owner/Session/receipt/PTY instance, both `workbenchLayouts` and both WorkspaceTab registries in **one SQLite transaction**. `tab_ids_in_layout` validates the pane split tree, unique Tab membership, group IDs and active pane. Both sides must exactly equal their full authoritative registry, with the moved Tab absent from source and present in destination. A missing/corrupt/changed layout returns `applied:false,recoveryRequired:true,reason:persisted_layout_inconsistent`; it never authorizes pending Journal deletion. The Host's in-memory Session proof still must match, and this read-only check does **not** resolve process death, cross-process lease or Host-crash outcome.

**Mobile named-view RPCs are capability-negotiated.** New `mobile.hello` advertises `terminalNamedViewLeaseV1`: this means the server understands explicit View ID on mobile attach/detach/restart and verifies a moved Tab's original receipt and sole attached live view before `tab.remove`. It is **not** the `tab.transfer` feature Gate. Even a new phone app's `MobileScopedTerminalViewLeaseClient` must check this authenticated Host capability before sending named RPCs or treating its view token as proof for moved-tab close. A legacy Host may silently ignore extra fields, so the new phone cannot grant close capabilities based on its own code version; the older Host path remains available for never-transferred terminals.

**Known detached windows block moved-Tab closing.** Desktop `WorkbenchTabLayoutOwner.closeWorkspaceTabs` now inspects `detachedTabWindows.isDetached` and `isLaunching` at the same **synchronous click-time snapshot** used to capture the original Tab/receipt/View ID. If the transferred Terminal still belongs to a Windows shared-engine or child-process detached window (including a temporarily unmounted/hidden surface), or the detach is pending, it requires merging back to the main window first. This preserves the D11 mounted-visibility count rule and blocks the known detached-but-not-mounted case. It cannot discover unregistered windows, different Apps, other devices or destroyed processes after restart; no durable last-view guarantee is claimed.

**Journal load and inventory agree on blockers.** `FileWorkbenchTerminalTransferJournal.loadPending()` now rejects *every* unexpected entry in its dedicated pending directory, including a symlink/directory named `.lock`, non-file `.json`, malformed hash or other filename. `inspectRecoveryInventory()` surfaces *all* these blockers read-only rather than suggesting an empty journal. This may also block `.DS_Store` or other extraneous files pending human verification, by design. PID and local archive are not Host-authoritative and no automatic safe unlock exists.

**Feature state:** `tab.transfer.capabilities.supported=false`, T2 not released. D13 checks limited to `rustfmt`, `dart format`, Git whitespace; no Cargo/Flutter tests, analyzer, Cargo check, build, real Win/Mac/Phone E2E, Push or Release. D14 still needs durable physical-Window/Device ownership, crash definitive recovery, process generation retirement and safe journal lock lifecycle.

## Historical T2-D12: observed PTY Exit evidence and named Mobile view lifecycle (2026-10-30)

The Host `handle_session_exit` now supplies the **actual original in-memory Session's** Tab ID, Workspace ID and `ptyInstanceToken` plus the real exit code to `RuntimeStore.record_transferred_terminal_exit`. This method is a separate SQLite transaction with an exact original `payloadJson` CAS, verifying the persisted terminal Tab, same Session ID, target Workspace, latest transfer receipt and original PTY generation. Only then it writes `payload.lastTerminalTabExit` with `transferMutationId`, Session/Workspace, original token, Exit Code and UTC. It does not delete the Tab or remove `lastTerminalTabTransfer`. A missing Session after a crash **cannot** fabricate this evidence.

The read-only `tab.transfer.status` distinguishes `reason:pty_exit_observed` from `pty_missing`／`pty_owner_mismatch` **only when** the Exit evidence matches the currently requested receipt, Session and Workspace. Response remains `applied:false,recoveryRequired:true` even with an observed normal exit; there is still no safe Host-crash compensation, definitive failure or authorization for renewed PTY generation/deletion/Journal release. The original live instance is gone after exit. Host crash between SQLite transfer commit and live Session reparent remains unresolved.

Mobile new code now uses the optional `MobileScopedTerminalViewLeaseClient` rather than altering the legacy `MobileTerminalClient` surface. Each existing phone Terminal controller generates one 24-byte `Random.secure()` view ID and reuses it for attach, transport reconnect, named detach and restart; Host `restart_terminal` rejects a token already registered to another active Host Client **before** killing its PTY, validates length and registers the requester as a named attached View in the new Session. Old clients remain unscoped; if an older client attempts to attach to a moved PTY the Host rejects it rather than minting a replacement token. Host Restart clears in-memory Client leases; the same token cannot prove the vanished original process survived a restart.

For transferred Terminal close on Mobile, `TabsController` synchronously reads a currently attached controller viewLeaseId (without creating a new UI attachment), and uses `MobileObservedViewLeaseTabRemoval` to send the original observed `tab.id`, Workspace, latest seen transfer Receipt and View ID directly to Actor-guarded `tab.remove`. **Do not send `terminal.terminate` before this request**: it kills the original live PTY and leaves the Tab undeletable under the D10 original-token proof. Missing controller, unready view, legacy client or stale receipt fails closed. Ordinary never-moved Terminal close remains unchanged; multiple phone/client restart windows and real device compatibility still need validation.

Journal `inspectRecoveryInventory` can now read all valid, damaged and locked pending records without `loadPending`'s fail-fast behavior. It makes **no writes and is not an atomic proof**. Local archive/PID metadata alone is not enough to unlock or declare a Host resolution.

**D12 remains gated OFF and unvalidated**: only `rustfmt`, `dart format` and Git whitespace checks; no Cargo/Flutter tests, Cargo check, analyzer, build, physical phone/Windows/macOS E2E, Push or Release. Continue D13 for durable owner and legitimate retired PTY cleanup.

**D12 audit follow-up**: An already persisted non-null malformed `lastTerminalTabExit` is never overwritten by another Exit event; it remains an unresolved evidence conflict. Journal Inventory also reports non-file/symlink objects with pending/`.lock`-shaped names without following them. Both still require explicit operator review and never imply successful recovery. Integrated `04aff070f` and `37bbe6b03`.

## Historical T2-D11: original view-bound Close and transferred natural-exit retention (2026-10-30)

For a previously transferred Terminal, Workbench now takes the **original UI attachment capability** at the same synchronous moment as the closing Tab snapshot: `Tab ID + observed Workspace + lastTerminalTabTransfer.id + attachedViewLeaseId`. The UI asks the existing `TerminalRuntimeAttachedViewLeaseSource` for a view token belonging to its already attached `TerminalHostPtySession`; it does **not** create/attach another PTY or request a fresh token from Host. An optional `WorkbenchViewBoundObservedTabCloseStore` and `WorkbenchViewBoundTabRemovalRepository` carry those immutable observations into `tab.remove` as `expectedWorkspaceId`, `expectedTransferMutationId` and `expectedViewLeaseId`. On a bounded timeout/disconnect replay, **all three remain identical**. Missing view or legacy Repository refuses destructive moved close; never fallback to unscoped removal. Ordinary Tabs retain the previous close path.

One Xterm Handle may be shared by multiple Flutter surfaces/OS native windows, yet D10 Host counts only one PTY viewLeaseId per handle. D11 refuses to disclose a Close token when that handle has **zero or multiple mounted visibility leases**; this stops known simultaneous mounted surfaces from masquerading as a sole viewer. A second *unmounted* window can still escape this local count, so this remains **not a fully trustworthy per-OS-window last-view lease**. The Host's generic `remove_terminal_session_tab` is also called automatically by `handle_session_exit` and from the `terminate` RPC. That prevents natural process exit from silently erasing Crash evidence; an exited transferred Tab **cannot yet be safely deleted through normal close** because the original live PTY instance can no longer be verified. ## Historical T2-D10: named per-view lease within one Host Session (2026-10-30)

A `TerminalHostPtySession` instance on Desktop now generates a stable random `viewLeaseId`, preserved through transport reconnect. The production Host port sends it on `createOrAttach`, `detach` and `terminate`, independent of the shared socket's numeric `client_id`. The Host `Session` now tracks `client_id -> Set<viewLeaseId>` alongside its original connection-level delivery cursors; detaching one token **does not** detach another view on the same Client. A token cannot register on two live Host clients simultaneously. Legacy unscoped attachments are separately remembered by `unscoped_clients`, including those sharing the same connection with a newer scoped View; they must **not** be mistaken for one known view. Mobile `terminal.attach` forwards an optional user-provided view ID but never manufactures one on behalf of an old phone.

For **transferred Terminal** the Host requires an explicit view ID to attach/detach; it refuses the old unscoped mobile/Desktop protocol. `terminate` requires both the authenticated I/O Client and its **sole attached viewLeaseId**, the original PTY instance token, the current Workspace/Tab and the exact observed transfer receipt. `tab.remove` may arrive over a separate authenticated Runtime Store connection, so it accepts `expectedViewLeaseId` as a bearer capability and requires that it is the **only attached live view**; relying on the mutation connection's numeric ID would reject legitimate users or confuse multiplexed windows. Source `tab.transfer` requires every attached Client to have named views; otherwise it refuses to move an unscoped PTY. Session leases are **in-memory only**, cleared on full Client disconnect/Host restart; they cannot reanimate the original PTY or replace durable Last-view ownership.

The read-only `tab.transfer.status` now also marks `receipt_conflict` and `persisted_owner_inconsistent` as `applied:false,recoveryRequired:true` instead of a plain negative. A newer receipt or split owner does not prove the original lost-reply operation failed, authorize a new mutation or permit Journal deletion. Desktop Journal has a separate read-only `inspectRecovery(tabId)` for pending readability, stale/active local lock, and exact local success archive; it does **not** unlock, delete, resolve Host failures or provide a Host-signed audit.

**Not yet usable**: Workbench `tab.remove` has not wired its current view token into `expectedViewLeaseId`, Host-crash recovery and durable Last-view Lease remain pending. The Host advertises `tab.transfer.capabilities.supported=false`. D10 ran only `rustfmt`, `dart format` and Git whitespace checks; no tests/analyzer/build/Win/Mac E2E, push or release. Existing Mobile clients and legacy unmoved terminals retain previous behavior; transferred terminals without explicit scope fail closed.

## Historical T2-D9: actual Client-bound last-view guard and no original-PTY remint (2026-10-30)

For **transferred** Terminal Tabs only, `tab.remove` now carries the authenticated *requesting Client ID* from the serialized queue into the Host Actor's preflight. Before allowing the worker to delete Tab metadata, the Actor confirms the latest persisted transfer receipt, its Workspace/Tab/Session, and the **original live PTY instance token** via the exact `tab.transfer.status` check. The requesting Client must itself still be in `Session.clients`, with **no other attached Host Client**, or deletion is rejected. A detached/stale requester cannot kill another Client's only PTY. The separate explicit `terminate` route also requires that this requester is attached and the live token matches, in addition to the D8 receipt/owner constraints. These are Host **Client connection** checks, not a unique per-window/per-device view identity; multiple views sharing one Host Client may remain indistinguishable.

For Workspace/Project/Managed/WorkspaceTabs/Sleep cleanup, the Host now refuses deletion of **any stored Tab carrying a transfer receipt**, even when no PTY is running or no viewers remain, so a crash-era receipt is not erased by an unrelated cascade. It additionally rejects running PTYs with the split SQLite/Session owner from an interrupted reparent. The current close policy is deliberately conservative: a transferred Tab with a missing original PTY, or a restarted/unverified generation, cannot be removed without a **future authoritative recovery workflow**. Detaching every viewer alone is not consent to kill the underlying process.

`createOrAttach` and mobile `terminal.attach` now require a live **original** PTY with a receipt-matching `ptyInstanceToken` for a moved Tab. The Host must not silently remint a Shell after restart or treat a new PTY with the same public Session ID as the original. The startup `spawnOnCreate` path refuses a moved Tab whose live PTY is gone, and `tab.upsert`'s generic spawn error cleanup must never delete that moved Tab or terminate its process. **Explicit `terminal.restart` on a transferred Tab is blocked** until an auditable PTY-generation replacement contract exists. Unmoved/legacy terminals keep their existing launch/restart behavior.

The Desktop App Support pending transfer Journal additionally has a per-Tab `.lock` acquired through exclusive file creation across App processes sharing this directory. A crash-stale lock is **not** automatically removed. A *caller-attested* confirmed Host receipt + both Workspace Layout readbacks is archived with exact original plan, a resolution marker and UTC timestamp **before** deleting Pending. This is a local audit (not a Host-signed, cross-device, or cross-restart last-view lease). Definitive Host rejection, safe manual stale-lock repair, normal transferred PTY exit cleanup, and process-generation renewal remain unimplemented.

## Historical T2-D8: original PTY-instance proof and attached-view cascade guard (2026-10-30)

A `tab.transfer` now writes `lastTerminalTabTransfer.ptyInstanceToken` in the **same SQLite transaction** that moves the Tab and both Layouts. The token combines an unpredictable **per-process Host epoch** with the in-memory `Session.instance_id` captured for the running PTY at commit. The host must check this token, the exact original Mutation ID, source/target Workspace, Session/Tab identity, and the current running PTY before `tab.transfer.status` can report `applied:true`. A restarted Host or reminted PTY may re-use the same public `sessionId`, but not this original token. Absent/mismatched tokens (including older D1–D7 receipts) yield `applied:false,recoveryRequired:true,reason:"pty_instance_unverified"`, and attempting to replay that exact `tab.transfer` with a newly spawned instance is rejected. This is **instance identity verification only**, not PTY resurrection or a proven rollback.

During destructive Workspace/Project operations (including `workspace.sleep` and `tab.removeForWorkspace`), an Actor preflight now rejects an attached, running Terminal with a persisted transfer receipt in any affected Workspace. Managed Workspace `close_sessions` first performs the same guard **before** capturing/terminating Sessions. The global runtime-mutation admission barrier prevents another client from attaching while a serialized cleanup is pending. - **Unknown transfer outcome:** A timeout/disconnect never means the transfer failed. The client queries `tab.transfer.status` with the *same* mutation ID and live PTY identity, and if unprovable, retains the unknown operation so a second move of that Tab cannot mint a fresh ID. ## Internal machinery

| Mechanism | Contract |
|---|---|
| PTY output | `handle_pty_output` appends to the scrollback and arms two independent batch tracks: `output_batch` (8 ms debounce or 64 KiB early flush) for client delivery and `durable_output_batch` (100 ms or 64 KiB) for `outputChunks` persistence, plus the debounced checkpoint timer |
| Output delivery | `flush_output_batch` pushes one `ClientFrame::Output` per attached, non-paused client on the bounded terminal lane (8 frames local, 32 mobile). Only an accepted frame advances that client's delivery cursor. A `Full` lane marks the client paused + resync-pending and arms a resync timer; a `Closed` lane schedules disconnect |
| `OutputResyncTick` | Emits `outputResyncRequired` on the terminal lane while the flag is pending; `Full` reschedules, `Closed` clears the flag and schedules disconnect. The client answers with `setOutputPaused` false, and a restart-resynced client always lands on the snapshot path because `attach_for_resync` dropped its cursor |
| Durable output | `persist_output_batch` runs `append_output(sessionId, sequence, data)` off the actor loop, tracked in `pending_output_writes` for the `await_output_writes` barrier (2 s). `append_output` only inserts while a `checkpoints` row exists, which is why `Session::start` writes its checkpoint before the session is reachable |
| Checkpoints | `CheckpointTick` (5 s debounce), `immediate_checkpoint` (detach, kept-on-exit, disconnect, dispose), and `handle_checkpoint_tick` all flush durable output, await pending writes, `write_checkpoint`, then `trim_session(scrollback_bytes)`. `terminate(false)` writes a final checkpoint; `terminate(true)` deletes checkpoint + chunks |
| PTY exit | `handle_session_exit` disarms the pulse, queues the exit push, cleans orchestration state; `Session::handle_exit` returns `None` on an already-exited session so a second event is a no-op. A kept failed setup or failed owned spawn gets `immediate_checkpoint`; otherwise `remove_terminal_session_tab` retires tab + session + history. When the tab row is already gone the session stays in the map not-running with a final checkpoint, and a later attach remints it |
| Client disconnect | `dispose_client` drops the client's orchestration waiters, cancels its queued runtime mutations, releases its mobile driver claims (restoring `desktop_dims`), cancels prompt uploads, detaches it from every session (forgetting delivery cursors), `immediate_checkpoint`s each session, then re-arms idle shutdown. The PTY survives: no client disconnect kills a session |
| Idle shutdown | `schedule_shutdown_if_idle` arms `empty_shutdown_delay_seconds` (30 s) when nothing runs and `detached_session_shutdown_delay_seconds` (3600 s) while sessions run; persistent mode, authenticated clients, jobs, mutations, the mobile gateway, coordinators, push subscriptions, and automations all cancel it. `handle_shutdown_tick` is generation-guarded: a stale tick is ignored, and a current tick runs `dispose()`, which terminates every session with `remove_history = false` so the final checkpoint and chunks survive for the next host start |
| `host.shutdown` / `host.restart` | Non-forced calls fail while agents, sessions, jobs, or push subscriptions are active; the reply is written before disposal through the ordered `ShutdownRuntimeAfterWrite`/`RestartRuntimeAfterWrite` markers. Mobile clients cannot call `host.shutdown` |

## Known gaps

- `createOrAttach` and `terminal.attach` never re-validate `workspaceId`/`tabId`/`workingDirectory`/`launch` against a live session; only `terminal.restart` checks metadata. A caller holding a stale but valid handle attaches to whatever PTY the handle names.
- `write` has no op id. Accept this for now: the client never retries writes, so a lost reply implies connection loss and reattach rather than a resend; deduplication by content is unsafe for a keystroke stream.
- `terminal_input_backpressure` is a typed `Conflict` code used by the orchestration Enter and Terminal Pulse retry paths; its wire message keeps the `terminal_input_backpressure: ...` prefix for older clients and compatibility matching.
- On the dead-handle path of `createOrAttach`, `take_terminal_restart_state` drops the old session (history preserved) before `launch` is validated, so a malformed launch still consumes the old PTY; the next call restores from the checkpoint.
- An exited session whose tab row was already removed stays in `sessions` as a not-running entry until an attach remints it or the host shuts down; `terminal.read` still serves its retained ring and `write` fails `not running`.
- Terminal Pulse configuration is persisted on the tab, but the armed rule is in memory: after a host restart `armed` reads false until the next `terminal.pulse.configure`.
