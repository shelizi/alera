# Tab and layout operation contract

This table answers the eight transaction/replay questions from the architecture refactor handoff (section 13) for every `tab.*` and `layout.*` request handled by `ServerActor`. Companion to `orchestration-operation-contract.md`, `project-operation-contract.md`, and `workspace-operation-contract.md`; update the table and its pinning tests together.

Authority is `ServerActor` on the terminal-host mailbox, persisting through `RuntimeStore`. Tabs are special in two ways: their `payload` carries host-owned fields (`agentTitle*` state) that client writes must not clobber, and `kind = "terminal"` tabs with `payload.spawnOnCreate` own a live PTY that is spawned as part of the upsert.

## T2-D15: never discard an invalid transfer/exit marker through older Tab operations (2026-10-30)

The latest transfer revision must continue to fence a close after an A→B→A Workspace switch. D15 additionally classifies an explicit (even null/malformed) `lastTerminalTabTransfer` **or** `lastTerminalTabExit` key as unresolved transfer evidence. Absent/blank ID/from/to/PTY token, mismatched Exit mutation/Workspace/Session/instance/Code, or an orphan Exit marker requires recovery; Host read-only `tab.transfer.status` returns `applied:false,recoveryRequired:true,reason:malformed_transfer_receipt`. Generic `terminate`/Attach/Restart, `tab.remove` preflight and serialized worker, natural Exit cleanup, Workspace/Project cascade must never treat these records as untransferred Tabs. A valid moved Tab still needs the only live exact UI View Token and original PTY Receipt for its guarded `tab.remove`.

Older `tab.upsert` may change a title, but may not change the `kind` or `workspaceId` of a transferred Tab, insert fake transfer/exit evidence for an unmoved Tab, overwrite the Host-owned original `terminalSessionId` or discard `lastTerminalTabExit` during stale UI edits. Mobile enforces the same shape before async close and disallows regular `removeObservedTab`/terminate-first paths for every Tab with transfer or original Exit evidence; even an Exit-only record fails closed.

The Journal resolved-archive folder now has its own **read-only inventory** of all local resolution files, including orphaned files whose Pending plan is gone, corrupt/non-file/symlink artifacts and SHA256 key mismatch. `localArchiveWellFormed` is not a Host proof, so `requiresHostVerification` remains true. No automatic stale-lock unlock, exited PTY legal retirement, durable cross-process Last-view Lease or crash compensating transaction was introduced in D15.

Capability remains `supported:false`. Only formatting and Git whitespace verification; no tests/analyzer/compile/Win-Mac-Phone E2E/Push/Release.

## Historical T2-D14: same-transaction returned Tab and no implicit Host-generation takeover (2026-10-30)

For a lost `tab.transfer` reply, `tab.transfer.status` can report `applied:true` only from the original *live* PTY/Session together with an exact current persisted transfer receipt and both persisted Workbench Layout/WorkspaceTab registries. D14 further changes the Store's `verify_terminal_transfer_layout_and_receipt` to return the **very Tab it validated inside the one SQLite read transaction** instead of a mere bool, preventing a stale pre-verification Tab from being returned under `applied:true`. The live PTY proof and SQLite transaction are still separate layers; no cross-Host write lock or recovery is implied.

The preexisting random process component of `ptyInstanceToken` now yields `applied:false,recoveryRequired:true,reason:host_generation_mismatch` when the persisted exact receipt has a different Host epoch. Another Host instance may still be alive, and no Client may treat this as failed transfer, permission to delete the Tab, clear Journal or start a replacement terminal. When Host actually persisted a matching original normal Exit event, it remains `pty_exit_observed` with `hostGenerationMismatch:true`, not an authorized cleanup. The legal atomic exited-Tab + Layout retirement transaction remains D15.

Mobile original View ID cannot silently migrate to a new socket while another Host Client owns it: normal named attach first, and only if Host explicitly rejects a duplicate ID may the phone request acknowledged old-client `detachTerminalWithViewLease` for the original Session, followed by one retry. This does not grant last-view ownership across a Host crash or two devices.

Journal pending/resolved evidence directory and per-file link type validation plus Tab-hash+Nonce+PID Lock release are fail-closed; read-only inspectors do not follow symlinks. No automated lock repair, Host determination or PID identity guarantee. Capability `supported:false`; no Cargo/Flutter Tests, Analyzer, Check, Build, Win/Mac/Phone E2E, Push/Release performed in D14.

## Historical T2-D13: all-Tab dual-layout authority and detached-view close veto (2026-10-30)

`tab.transfer.status` returns `applied:true` only if live original PTY, latest persisted receipt **and both persisted Workspace Layouts and WorkspaceTab registries** all agree. The Host adds a single SQLite read transaction that verifies exact original transfer identity, source missing the moved Tab, target containing it exactly once, syntactically valid pane/split tree and the entire Tab set on each side. Inconsistency results in `applied:false,recoveryRequired:true,reason:persisted_layout_inconsistent`. Callers retain the pending transfer and **must not** silently discard a disputed layout. The snapshot is read-only and does not provide Host Crash repair, a safe reverse transfer or a dead PTY cleanup contract.

The Workbench's view-bound Close now consults its already existing native/child Detached Window registry in the same synchronous click-time pass as the Tab and lease snapshot: any known detached or launching moved Terminal is rejected until it returns to the primary window, even if its second native Surface is currently unmounted and D11's visibility count would have been one. This guard covers only windows registered to the local App; multi-process/Host restart durable view ownership is still unimplemented.

Mobile's new `terminalNamedViewLeaseV1` capability is explicit in authenticated `mobile.hello` and mandatory before the phone sends per-view attach/detach/restart or `MobileObservedViewLeaseTabRemoval` for moved Tabs. An old Host ignoring JSON View ID fields cannot be treated as a verified lease authority. Mobile still preserves never-moved legacy calls.

Journal's fail-closed loader rejects all unexpected directory entries; the read-only inventory now lists every blocker, not only `.json` or `.lock` entries. This detects malicious/malformed symlinks and benign extraneous files alike without deleting them. No Host-signed resolution, cross-process liveness proof or safe stale Lock repair yet. T2 `supported:false`; no Cargo/Flutter tests, analyzer, compile, Win/Mac/Phone E2E, Push or Release in D13.

## Historical T2-D12: Mobile close transaction and exact observed exit diagnostic (2026-10-30)

Transferred `tab.remove` now also has a narrow Mobile caller: the phone `TabsController` requires an already live `TerminalSessionController` and the same random `viewLeaseId` it passed to `terminal.attach`. It snapshots this before the first `await`, retains the pre-dialog `WorkspaceTabSummary` receipt/owner, and calls `MobileObservedViewLeaseTabRemoval.removeObservedTabWithViewLease`, producing the **same three expected fields** as Desktop: `expectedWorkspaceId`, `expectedTransferMutationId`, `expectedViewLeaseId`. Crucially, the old two-step `terminal.terminate` → `tab.remove` is forbidden for moved Tabs; the serialized Actor owns authoritative last-view, persisted receipt and original instance checks before deleting anything. Old Mobile clients without the named view Port fail closed. Never-moved Tabs keep their old close order.

Natural PTY exit now attempts an exact Store `record_transferred_terminal_exit` CAS before the generic Session-exit retention path. This stores `lastTerminalTabExit` **only when the real Host original Session emits Exit and persisted Tab/Receipt/Instance match**; a crash without that observed event has no marker. `tab.transfer.status` can return `pty_exit_observed` to distinguish the events, but `applied` remains false and `recoveryRequired` true: an exit marker is **not** permission for arbitrary `tab.remove`, cascade, silent rollback, remint or Journal clearing. Legally retiring exited moved Tabs still needs a new proof-bound transaction.

Desktop Journal `inspectRecoveryInventory` is an inspection-only report across valid/invalid `.json`／`.lock` filenames, corrupt payloads, local audit, lock metadata and SHA key mismatch. It cannot independently validate the Host outcome or safely repair an abandoned lock. Host's advertised `tab.transfer.capabilities.supported=false` remains OFF. D12 had formatting and Git whitespace verification only: no Cargo/Flutter tests, analyzer, build, Phone/Win/Mac E2E, Push or Release.

**D12 audit follow-up**: Store's `lastTerminalTabExit` CAS refuses to replace non-null malformed evidence; Journal Inventory identifies symlink/directory entries masquerading as pending/`.lock` without traversing them. No autonomous cleanup follows either finding. Integrated `04aff070f` and `37bbe6b03`.

## Historical T2-D11: click-time View capability, no implicit exited-Tab receipt deletion (2026-10-30)

Transferred Terminal `tab.remove` is now initiated by a **view-bound observed close**. At synchronous close click, Workbench snapshots its current `WorkspaceTabRecord` including the latest **observed** `lastTerminalTabTransfer.id`, the displayed Workspace and the `viewLeaseId` of the *same already-attached local PTY view*. No new Host lookup, session creation or token renewal is allowed later. `WorkbenchTabCloseCoordinator` fails closed when the observed Tab is moved but this token or the optional ViewBound Store/Repo port is unavailable. The Runtime Host request includes `expectedWorkspaceId`, `expectedTransferMutationId`, `expectedViewLeaseId`; timeout / connection-close retries repeat the **same original request scope**, preventing A→B→A or another window's updated token from being substituted.

A shared Xterm Handle represents only one Host PTY Lease even when several mounted Flutter TerminalSurface instances are open. The current UI refuses the close capability when the Handle has zero or more than one mounted visibility lease. This is a conservative **partial** local guard: a hidden/unmounted window or different process cannot be proven absent merely by counting mounted Flutter surfaces. The Host's original-live-PTY check and per-Client View Lease barriers continue to apply.

`handle_session_exit` and the ordinary `terminal.terminate` cleanup both route through `remove_terminal_session_tab`. It now preserves every transferred Terminal's persisted Tab and Receipt rather than silently deleting them when the process exited; ordinary never-transferred terminal exit cleanup is unchanged. This is deliberate evidence preservation, **not a production-ready legal retired/dead Terminal cleanup**. Workspace/Project cascade still rejects persisted moved receipts. D12 must introduce explicit safe lifecycle retirement under verifiable original process generation and Host crash outcomes.

`FileWorkbenchTerminalTransferJournal` now writes a per-lock random nonce, PID, UTC timestamp and tab hash after exclusive create. Only the same lock owner can normally delete it, and the per-Tab inspector may report evidence validity, but malformed/stale locks remain blocked pending an independent manual recovery workflow; local metadata is neither Host-signed proof nor process-liveness evidence. `tab.transfer.capabilities.supported=false`; no Cargo/Flutter tests, analyzer, build, Windows/macOS E2E, Push/Release. D11 only formatting and Git whitespace validation.

## Historical T2-D10: unique live View Token required to close transferred Tabs (2026-10-30)

Serialized `tab.remove` now includes an **optional `expectedViewLeaseId`**. It remains optional for never-transferred legacy Tabs, but for any transferred Terminal the Actor requires the exact latest persisted receipt, verified original live PTY instance and a view token that **is the sole active lease across all Host clients**. Runtime-store mutations may use an authenticated connection other than the PTY I/O socket: the unguessable view token is therefore the capability proof, not that request socket's transient Client ID. Other active views, unscoped legacy attachments sharing a Client, missing Token, Host restart or process-owner divergence cause fail-closed rejection before the SQLite row is removed.

The Host `Session` has ephemeral per-client View Lease IDs and a separate unscoped-attachment set. Desktop `TerminalHostPtySession` passes its per-instance UUID through create/attach, detach and explicit terminate; mobile forwards an optional supplied View Token without inventing identity for an outdated app. `tab.transfer` refuses to move any PTY with attached clients whose views have not been independently named. This is **not durable** across Host restart or across heterogeneous clients, and Workbench Tab Close has **not yet forwarded** its original current UI view token to `tab.remove`; a legitimate moved-Tab close still fails closed until that D11 wiring is complete.

`tab.transfer.status` now reports `receipt_conflict` or `persisted_owner_inconsistent` as explicit `recoveryRequired:true` cases rather than treating a conflicting persisted receipt as a safe negative. The Desktop per-Tab Journal offers an **inspection-only** recovery snapshot of `.lock`, Pending parse status and local archived proof; it cannot remove an active/stale Lock or mark definitive Host failure. PTY generation renewal, dead transferred Tab lawful cleanup and complete mobile/backward compatibility remain blockers. Host `supported:false` stays off. No Cargo/Flutter tests, analyzer, build, Windows/macOS E2E, Push or Release were run; only formatting and Git whitespace checks.

## Historical T2-D9: Host requester identity, retained crash receipt and local Journal audit (2026-10-30)

The `tab.remove` serialized Host command now passes its **actual authenticated `client_id`** to the Actor preflight instead of using the transfer receipt alone. For Tabs with `lastTerminalTabTransfer`, the Host re-queries the exact Receipt + live PTY `ptyInstanceToken` via `tab.transfer.status` and requires the requester to be an **attached Client with no other attached Client**. A missing/dead/reminted PTY, stale Client or other viewer means no destructive removal. This still counts Host *connections*, not a durable Last-view Lease for multiple windows on one Client.

All serialized workspace/project/managed/WorkspaceTabs/Sleep cascades now refuse when any affected Workspace still has a persisted transferred Terminal Tab **even if its PTY has exited or disappeared after a crash**. They also refuse an in-memory running PTY whose original Host Workspace disagrees with the persisted Tab's new Workspace. Preserving evidence takes precedence over automatic cleanup; future explicit successful/failed recovery and final Tab disposal are required.

`createOrAttach`, `terminal.attach`, `spawnOnCreate` and `terminal.restart` are now fail-closed for transferred Tabs that cannot prove the **original** PTY generation (restart currently refused on all transferred Tabs), rather than silently replacing it and destroying its last transfer receipt's meaning. `tab.upsert` spawn failure cannot remove a transferred Tab through generic cleanup. `FileWorkbenchTerminalTransferJournal` uses a per-Tab exclusive cross-App `.lock` for remember/forget. Only after Host proof and both Layout readbacks does the caller write a flushed, exact-plan **local resolution archive** and remove Pending; an interrupted lock or missing/mismatched archive fails closed. This is not a signed Host completion proof, Host crash recovery, or globally distributed View lease.

**Feature `tab.transfer.capabilities.supported=false` remains disabled.** D9 modifications have **not** been tested, compiled, analyzed or exercised on Windows/macOS. Only formatting and scoped Git whitespace checks completed; no push/release. D10 must provide normal transferred PTY exit/cleanup policy, authoritative crash/failure resolution, per-window lease, stale-lock manual repair and E2E.

## Historical T2-D8: transfer receipt instance proof and cascade preflight (2026-10-30)

`transfer_terminal_tab_storage` now additionally requires a nonempty `pty_instance_token` computed by the owning Host from a per-process random epoch and its live `Session.instance_id`. Its `lastTerminalTabTransfer.ptyInstanceToken` is stored **atomically with** the Tab owner and both Workspace Layouts. The same Session handle after a Host crash/restart or PTY restart is **not** proof of the original process: `tab.transfer.status` returns `recoveryRequired:true,reason:"pty_instance_unverified"` if this proof is absent/stale, and an exact-ID Store replay cannot be promoted to Host success when a newly spawned PTY has a different token. Old receipts without proof fail closed, not as automatic failure or rollback.

To prevent `RemoveWorkspace`/`RemoveProject`/`RemoveProjectWorkspaces`/`RemoveManagedWorkspace`/`RemoveWorkspaceTabs`/`SleepWorkspace` from bypassing Tab-specific close validation, their actor preflight now checks whether an affected Workspace still has a **live, attached** transferred Terminal. If so, the whole cleanup is refused until the viewers detach. The latter two routes now also enter Actor preflight before background Store deletion. This is single-Host attached-view protection; fully detached Sessions and crash-era cross-process leases are **not** solved.

Desktop `confirmUnknownTerminalTransfer` locks the original Tab+Mutation locally through status proof, both Workspace Tab/Layout reconciliation passes and Journal forget. Repeated local `Check status` clicks cannot race to release the original persistent guard. Host definitive rejection, manual safe clearing, multi-App ownership and real Crash recovery are still pending; capability stays `supported:false`. D8 ran only formatting and scoped Git whitespace checks, **not** tests, analyzer, build, Win/Mac E2E, push or release.

## Historical T2-D7: removal/attach race and explicit incomplete-recovery outcome (2026-10-30)

While a `tab.remove` request is **queued or executing**, the Host Actor's in-memory removal fence rejects any new `createOrAttach`/`terminal.attach` and explicit `terminate` targeting that Tab. The fence is checked even if the background Store operation has already deleted the Tab row but the Actor has not yet applied `TabRemoved`. A normal `detach` only releases its own view and never kills the PTY. The fence protects this single `RemoveTab` race; it does **not** replace a global last-view lease or cover Workspace/Project cascade removal.

`tab.transfer.status` now distinguishes three states: (1) matching receipt **and** running target PTY -> `applied:true`; (2) matching receipt with missing, dead, or mismatched PTY -> `applied:false,recoveryRequired:true` with `pty_missing` or `pty_owner_mismatch`; (3) no exact matching receipt -> `applied:false` (outcome remains unknown). Desktop maps state (2) to a dedicated unresolved warning, preserving the original per-Tab App Support Journal until a future authoritative recovery and both-Layout reconciliation. The Host does not automatically recreate PTY, roll back SQLite, or declare permanent failure.

This is unverified, capability-gated source code: `tab.transfer.capabilities.supported=false`, only source formatting and whitespace checks, **no** Cargo/Flutter tests, analyzer, build, Win/Mac E2E, push or release. Full Host crash owner recovery and cross-process last-view lease remain future work.

## T2-D6: mandatory observed receipt, exact source-pane prune, exclusive journal (2026-10-30)

On **every** serialized `tab.remove`, a Terminal with a persisted `lastTerminalTabTransfer` object now **requires** `expectedTransferMutationId` equal to the Host's latest recorded receipt, as well as the correct `expectedWorkspaceId`. Supplying only a Workspace ID is no longer sufficient, even for a legacy Desktop close after A→B→A. Untouched/never-transferred tabs keep their previous closing contract. The Desktop Workbench close flow now captures the **observed Tab snapshot before any asynchronous close** and forwards its receipt through the optional `WorkbenchObservedTabCloseStore` / `WorkbenchObservedTabRemovalRepository` to `tab.remove`, reusing the same payload after timeout/disconnect. It does **not** fetch the current Host receipt to authorize a stale view; older repositories fail closed on moved terminals. The D5+ optional-receipt statement below is historical.

Atomic `transfer_terminal_tab_storage` source-layout validation now mirrors `WorkbenchLayoutNode.pruneGroups`: when a source pane becomes empty, remove its leaf and promote the surviving subtree, preserving untouched split axes/ratios and the valid active pane. When the last source pane is removed, require exactly one empty `{workspaceId}/main` leaf. Unrelated source geometry modifications are rejected instead of being accepted merely because total Tab membership is unchanged.

`FileWorkbenchTerminalTransferJournal.remember` now claims the per-Tab file with `File.create(exclusive:true)` **before issuing the Host RPC**. Two local App processes using the same Support Directory cannot overwrite one another's original transfer intent by racing through `exists + rename`. An interrupted write leaves a fail-closed unreadable sentinel; users must verify/repair it rather than mint a replacement operation ID. This is *not* a distributed Host/PTy lease, transactional fsync directory, proof of Host commit, or automatic Host crash recovery. This D6 source change is **not compiled, tested or enabled**; `tab.transfer.capabilities.supported=false` remains the external contract.

## T2-D5+: persisted lost-reply intent and Mobile Tab Remove receipt (2026-10-30)

The Desktop `WorkbenchTerminalTabTransferCoordinator` now has an App Support Directory-backed per-Tab `FileWorkbenchTerminalTransferJournal`: a new transfer writes its **exact** mutation ID, Session, source/target Workspaces and proposed/expected Layouts **before** making `tab.transfer`. On App restart, journal restoration happens before a new transfer or manual Check status. No client mints a replacement ID for an unresolved record. A positive Host status **plus successful readback of both authoritative Workspace layouts** is required before removing the journal. A corrupt or inaccessible journal fails closed rather than being treated as empty. The former D4 section below describes the old **in-memory-only** state and is historical.

For `tab.remove`, the serialized request accepts an **optional** `expectedTransferMutationId` in addition to the expected Workspace. When supplied (now sent by observed-snapshot Mobile close), the current persisted `lastTerminalTabTransfer.id` must match, rejecting A→B→A stale removals. Legacy Desktop requests without the optional receipt still use the older Workspace guard and therefore **do not** have full ABA protection on this route. Removing a transferred live Terminal is also rejected by Host Actor preflight when more than one client is attached; this is not a complete distributed ownership lease.

The local Journal is not a distributed lock: concurrent App processes and a Host crash between SQLite commit and active PTY reconciliation remain unresolved, as does distinguishing a definitively rejected transfer from an unknown outcome before manually clearing a pending record. These changes are integrated but `tab.transfer.capabilities.supported=false`; no Flutter/Cargo tests, analyzer, build, Windows/macOS E2E, push or release occurred for D5+.

## T2-D5: transfer-only pane delta and authoritative readback (2026-10-30)

`RuntimeStore::transfer_terminal_tab_storage` now checks that the client's **replacement** source/target Layouts do more than preserve the same overall Tab set: existing source groups may lose only the transferred Tab (plus empty-pane pruning), and existing destination groups may gain only that Tab, appended to its chosen Pane with that Tab active. Other panes' ordered Tab IDs and active selections must not change. The destination Split Tree must match the stored snapshot. The source Split Tree is checked for equality when no Pane is pruned; **exact tree-prune equivalence when source Panes disappear remains a narrower unverified edge**, not a general Layout revision CAS.

`WorkbenchTerminalTransferReconciliation` verifies every Tab maps to one group, correct owning Workspace, an existing active Pane and a consistent Split Tree before updating UI. It performs a second **non-transactional** source/target Tabs+Layouts readback and refuses stale/changing snapshots without persisting them. Two read passes improve safety but do **not** constitute a multi-Workspace atomic snapshot. Capability remains `tab.transfer.capabilities.supported=false`; none of these changes have been compiled or regression-tested in D5.

## T2-D4: lost transfer reply and dual-layout authority (2026-10-30)

The `tab.transfer` request is a **single atomic owner/Layout mutation** scoped to one existing, live Terminal Session. A lost response is not proof of failure. The client holds its exact `clientMutationId` and both source/target identities, queries `tab.transfer.status`, and accepts success **only** when the Host confirms the original persisted receipt **and** current live PTY ownership. Client-side `WorkbenchTerminalTabTransferCoordinator` must retain this unknown-outcome guard until `WorkbenchTerminalTransferReconciliation` has read and applied **both** authoritative Tab lists and Layouts without further persistence. Mismatched replies also remain unknown. This protection is currently **in-memory only** (not preserved across application restarts).

Host `layout.upsert` has a D3 narrow ownership membership fence for Tabs with `lastTerminalTabTransfer`; it is **not** universal optimistic CAS for every Workbench Layout edit. Transferred Tabs remain feature-gated off with `tab.transfer.capabilities.supported=false`. Source/target listeners must not use old provisional sanitized layouts to overwrite the Host's atomic results. These are unverified implementation contracts, **not** evidence of passing tests or release readiness.

Invariants worth keeping visible:

- A never-transferred `tab.upsert` that fails its `spawnOnCreate` spawn retains the legacy rollback order (remove-row then terminate-sessions). **D9 transferred Terminal exception**: moved Tab/transfer receipt and its existing PTY are always preserved on spawn failure; the Host blocks unsafe remint before destructive fallback cleanup.
- `tab.remove` cancels the agent-title job on the actor before the mutation is enqueued, so an in-flight title write cannot resurrect a removed tab's title state.
- Startup reconciliation ordinarily removes a failed spawn-on-create row, **except** a previously transferred Terminal: a missing original launch directory or unsafe remint keeps the Tab row for recovery rather than destroying its durable ownership.
- Layout writes from legacy clients must not overwrite terminal ownership already transferred by a separate window; the Store's D3 membership fence is enforced even when the Flutter watcher did not run.
