Base: main 0e87e230b, including all nine workspace-search phases. This phase is scoped to Dart workbench catalog reconciliation and initialization; no Rust/FRB or Git mutation API changes.

## Changes

- `WorkspaceService.ensureMainWorkspace` now preserves an unchanged main record, including its timestamp. It compares the actual fields owned by preparation (name, branch, path, kind, status, source branch and reuses-existing-branch flag). It does not rewrite the same record or trigger a redundant workspace.upsert event. Actual branch/name/path/kind repairs, same-checkout duplicate tab migration and legacy main-to-linked demotion still execute.
- `reconcile` reuses its last authoritative catalog list when no mutations occur after that read, instead of another workspace.list call. Uses already-resolved canonical keys for live worktree identity, while retaining fresh path checks and existing fail-closed pruning when the Git list fails or omits the main checkout. Mutation cases still read the persisted final list.
- The main workspace preparation coordinator invokes reconciliation once (reconcile already ensures the main workspace) and shares the actual in-flight Future per project. Concurrent different project preparations remain independent. Bootstrap completion no longer clears an error reported by the preparation callback.
- The controller test repository now publishes its initial snapshot on subscribe, matching both actual Runtime and Drift repositories. Its recovery fixture represents a live Git worktree after reconciliation, not a stale database-only row. Fixed a duplicate project ID in the 15-project startup test, which previously caused a legitimate legacy-main repair.

## Phase 2 — bounded background worktree metadata and reconciliation scheduling

Phase 1 was fast-forward merged into local main at b586a1f65 with existing unrelated history edits preserved. Phase 2 started from that exact commit in a clean isolated branch.

The production WorkbenchWorktreeMetadataWatcherRegistry owns two independent FIFO task pools, each with four concurrent slots by default: authoritative automatic worktree reconciliation and filesystem metadata probes. Each registered GitWorktreeMetadataWatcher retains at most one outstanding pass per pool and a trailing dirty flag. Requests received before a queued pass actually starts are covered by that pass; changes during actual I/O request a trailing pass, which rejoins the FIFO rather than monopolizing a slot. Failed callbacks release slots. Queued callbacks from retired watchers are cancelled and stale registry callbacks are fenced by watcher identity. Suspending for a local worktree mutation cancels that watcher's queued refresh, retains its pending flag and waits only for its own in-flight callback; resume replays the flag. Existing active operations are not forcibly cancelled. Disposal cancels pending callbacks and timers, and retains the existing wait for in-flight local work.

The original 300 ms quiet debounce now has a non-resetting 1 s deadline for scheduling automatic reconciliation. This is an admission deadline, not a guarantee of completion within one second: shared-pool contention and slow Git/filesystem work can delay actual completion. The original 60 s recovery poll, metadata probe recovery and authoritative Git checks remain. There is no new cache, no dropped structural event, no change to Git mutation semantics, and no new dependency. This limits watcher-triggered background work per workbench registry; ordinary startup preparation and explicit manual operations do not go through these pools. Both pools can be active simultaneously (up to eight total background callbacks per registry), and the number of queued jobs scales with live projects. Per-project timers are retained; the scheduler bounds the concurrent work rather than claiming to eliminate all timers or CPU usage.

Validation: 100 actual watcher objects share the two pools, with injected filesystem/refresh callbacks. The initial 100 probes run in FIFO order with peak four active. All 100 project refreshes are queued, the first four are held active, and another 960 notifications are delivered to the remaining 96 queued projects. Exactly 100 refresh callbacks finish, in FIFO order, with peak four active; no redundant trailing passes for pre-start events. Additional tests cover slot release on failure, owner-specific cancellation, pending refresh suspension and resume without waiting for another project's blocked operation, pending probe/refresh retirement, stale watcher callback fencing, and a deterministic fake-clock test with 100 ms quiet / 250 ms maximum (12 events at 50 ms, two maximum-deadline passes and one trailing quiet pass). This is callback-count/concurrency validation, not real repository CPU, IPC or wall-clock benchmarking. Existing controller regression exercises actual metadata watcher integration.

The first focused test run was stopped after its Flutter widget-test clock stalled on stream cancellation; verified only that operation's process tree was terminated. The second run's fake clock passed deadline assertions but failed the synchronous cleanup-completion assertion. Separated outer-zone cancellation completion from deterministic timer assertions, then all 21 watcher/registry tests passed. Added failure-slot test and ran the complete 14-file regression: 279 passed, zero failed (16 s Flutter test output, 27.687 s managed job). Formatting and diff checks passed. No Rust/FRB changes and no packaged desktop benchmark. Phase 2 remains a separate commit until explicitly merged; no remote push, release or deployment.

## Phase 3 — coalesced Git fast-action background metadata

The Source Control controller now retains one running fast-action repository metadata read and at most one pending request (latest generation) per controller. Stage/unstage/explicit refresh continue to publish file status immediately and retain existing mutation and watcher behavior. A manual refresh's stash requirement is sticky until a current metadata read or an authoritative full snapshot satisfies it; a stale read cannot publish, a failed read releases the slot, and disposal clears pending work. This bounds fast-action background reads, not all Git I/O: full snapshots (including watcher reconciliation) remain authoritative and may overlap a slow fast-action metadata read. An already running backend query is not cancelled; the trailing metadata read waits for it to finish. No repository or stash freshness cache, altered Git command semantics, new dependencies, Rust/FRB changes, or generated API changes.

Validation: a blocked first metadata read during one manual refresh and 20 sequential stage operations still allows all 20 file-status updates. The new controller makes exactly two repository-state calls for those 21 fast actions (one in flight, one latest trailing read), peak one active, and two stash queries because the superseded manual stash refresh is preserved. The previous execution path would launch 21 repository-state calls under this fixture; the 90.5% reduction is an operation-count comparison against the old path, not measured real Git process latency or CPU. Tests also cover stale completion suppression, metadata failure releasing a pending request, and disposal not starting queued work.

Focused controller suite: 17 passed, zero failed. Regenerated the annotated Riverpod controller's source hash with the official pinned generator; the filtered generation unexpectedly removed 90 unrelated tracked generated files, which were restored byte-for-byte from HEAD, preserving only the intended hash change. Final Dart formatting and diff checks passed. Expanded 17-file Flutter regression: 299 passed, zero failed (including source control state/diff/mutations, workbench and workspace catalog, watcher pools, auto-fetch, Git change groups and selection, multi-repository sidebar, worktree branch menu, source-control list and icons).
