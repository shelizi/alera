## Phase 2 — bounded background worktree metadata and reconciliation scheduling

Phase 1 was fast-forward merged into local main at b586a1f65 with existing unrelated history edits preserved. Phase 2 started from that exact commit in a clean isolated branch.

The production WorkbenchWorktreeMetadataWatcherRegistry owns two independent FIFO task pools, each with four concurrent slots by default: authoritative automatic worktree reconciliation and filesystem metadata probes. Each registered GitWorktreeMetadataWatcher retains at most one outstanding pass per pool and a trailing dirty flag. Requests received before a queued pass actually starts are covered by that pass; changes during actual I/O request a trailing pass, which rejoins the FIFO rather than monopolizing a slot. Failed callbacks release slots. Queued callbacks from retired watchers are cancelled and stale registry callbacks are fenced by watcher identity. Suspending for a local worktree mutation cancels that watcher's queued refresh, retains its pending flag and waits only for its own in-flight callback; resume replays the flag. Existing active operations are not forcibly cancelled. Disposal cancels pending callbacks and timers, and retains the existing wait for in-flight local work.

The original 300 ms quiet debounce now has a non-resetting 1 s deadline for scheduling automatic reconciliation. This is an admission deadline, not a guarantee of completion within one second: shared-pool contention and slow Git/filesystem work can delay actual completion. The original 60 s recovery poll, metadata probe recovery and authoritative Git checks remain. There is no new cache, no dropped structural event, no change to Git mutation semantics, and no new dependency. This limits watcher-triggered background work per workbench registry; ordinary startup preparation and explicit manual operations do not go through these pools. Both pools can be active simultaneously (up to eight total background callbacks per registry), and the number of queued jobs scales with live projects. Per-project timers are retained; the scheduler bounds the concurrent work rather than claiming to eliminate all timers or CPU usage.
