- `WorkspaceService.ensureMainWorkspace` now preserves an unchanged main record, including its timestamp. Its recovery fixture represents a live Git worktree after reconciliation, not a stale database-only row. Fixed a duplicate project ID in the 15-project startup test, which previously caused a legitimate legacy-main repair.

## Phase 2 — bounded background worktree metadata and reconciliation scheduling

Phase 1 was fast-forward merged into local main at b586a1f65 with existing unrelated history edits preserved. Phase 2 started from that exact commit in a clean isolated branch.

The production WorkbenchWorktreeMetadataWatcherRegistry owns two independent FIFO task pools, each with four concurrent slots by default: authoritative automatic worktree reconciliation and filesystem metadata probes. Each registered GitWorktreeMetadataWatcher retains at most one outstanding pass per pool and a trailing dirty flag. Requests received before a queued pass actually starts are covered by that pass; changes during actual I/O request a trailing pass, which rejoins the FIFO rather than monopolizing a slot. Failed callbacks release slots. Queued callbacks from retired watchers are cancelled and stale registry callbacks are fenced by watcher identity. Suspending for a local worktree mutation cancels that watcher's queued refresh, retains its pending flag and waits only for its own in-flight callback; resume replays the flag. Existing active operations are not forcibly cancelled. Disposal cancels pending callbacks and timers, and retains the existing wait for in-flight local work.

The original 300 ms quiet debounce now has a non-resetting 1 s deadline for scheduling automatic reconciliation. This is an admission deadline, not a guarantee of completion within one second: shared-pool contention and slow Git/filesystem work can delay actual completion. The original 60 s recovery poll, metadata probe recovery and authoritative Git checks remain. There is no new cache, no dropped structural event, no change to Git mutation semantics, and no new dependency. This limits watcher-triggered background work per workbench registry; ordinary startup preparation and explicit manual operations do not go through these pools. Both pools can be active simultaneously (up to eight total background callbacks per registry), and the number of queued jobs scales with live projects. Per-project timers are retained; the scheduler bounds the concurrent work rather than claiming to eliminate all timers or CPU usage.

Validation: 100 actual watcher objects share the two pools, with injected filesystem/refresh callbacks. The initial 100 probes run in FIFO order with peak four active. All 100 project refreshes are queued, the first four are held active, and another 960 notifications are delivered to the remaining 96 queued projects. Exactly 100 refresh callbacks finish, in FIFO order, with peak four active; no redundant trailing passes for pre-start events. Additional tests cover slot release on failure, owner-specific cancellation, pending refresh suspension and resume without waiting for another project's blocked operation, pending probe/refresh retirement, stale watcher callback fencing, and a deterministic fake-clock test with 100 ms quiet / 250 ms maximum (12 events at 50 ms, two maximum-deadline passes and one trailing quiet pass). This is callback-count/concurrency validation, not real repository CPU, IPC or wall-clock benchmarking. Existing controller regression exercises actual metadata watcher integration.

The first focused test run was stopped after its Flutter widget-test clock stalled on stream cancellation; verified only that operation's process tree was terminated. The second run's fake clock passed deadline assertions but failed the synchronous cleanup-completion assertion. Separated outer-zone cancellation completion from deterministic timer assertions, then all 21 watcher/registry tests passed. Added failure-slot test and ran the complete 14-file regression: 279 passed, zero failed (16 s Flutter test output, 27.687 s managed job). Formatting and diff checks passed. ## Phase 3 — coalesced Git fast-action background metadata

The Source Control controller now retains one running fast-action repository metadata read and at most one pending request (latest generation) per controller. Stage/unstage/explicit refresh continue to publish file status immediately and retain existing mutation and watcher behavior. A manual refresh's stash requirement is sticky until a current metadata read or an authoritative full snapshot satisfies it; a stale read cannot publish, a failed read releases the slot, and disposal clears pending work. This bounds fast-action background reads, not all Git I/O: full snapshots (including watcher reconciliation) remain authoritative and may overlap a slow fast-action metadata read. An already running backend query is not cancelled; the trailing metadata read waits for it to finish. No repository or stash freshness cache, altered Git command semantics, new dependencies, Rust/FRB changes, or generated API changes.

## Phase 5 — bounded batch Source Control line statistics

Full status keeps the existing libgit2 authoritative status options and ordered change/group projections. Only same-path, same-mode ordinary regular-file modifications with UTF-8 paths and no submodule metadata enter a per-request stats plan. Stage and worktree stats are separated into batches of at most 64 literal pathspecs; the actual diff must contain exactly one ordinary modified delta for each expected path and no unexpected, duplicate, missing, renamed, copied, added or removed delta. The batch uses the same patch-origin counting and binary/no-visible-line semantics as the original individual collector. Single-file batches, uncertain delta shapes and batch errors fall back to the original per-file diff path, including its existing renderer tolerance. Adds/deletes, renames, conflicts, mode/type changes and gitlinks are not optimized by this path. No shared state, persistent cache, public bridge change or new dependency. Concurrent external edits still do not form an atomic filesystem snapshot, consistent with the original status API.

## Phase 7 — cross-worktree Source Control automatic refresh admission

The per-controller watcher debounce/cooldown and single in-flight status guard did not limit concurrent full snapshots across different worktree controllers. Reuse the existing FIFO WorkbenchBackgroundTaskPool through a provider-scoped pool with four slots. Only automatic watcher snapshots are admitted; initial loads, manual refreshes, foreground mutations and fast-action metadata are not throttled by this pool. Each owner holds at most one queued/active refresh; events received while waiting for admission are covered by the upcoming current-state read. Allocate a load generation on actual admission, recheck whether a foreground action is busy, retain trailing reloads for changes during execution, and cancel queued callbacks on disposal. A started callback holds its slot until it really finishes. Preserve equal-summary history invalidation, reconciled payload instances, existing debounce, cooldown and stale-completion checks. No persistent status cache, native API, or mutation changes.

Controlled Flutter workload: 100 active worktree controllers within one ProviderContainer, all signaled, four held at a status gate, 96 queued; 960 additional notifications on waiting worktrees, one newer active-worktree edit and one disposed waiting owner. Observed peak four status reads; FIFO order, 99 first passes plus exactly one trailing pass (100 total), disposed owner never scanned and all surviving worktree statuses correct. Old implementation had no cross-controller cap (100 potential simultaneous scans for 100 owners); no measured old runtime or hardware CPU/I/O percentage. Each admitted snapshot may issue three concurrent underlying reads. Other foreground loads can run concurrently, so four is not a process-wide native thread/I/O cap. The four-slot choice trades off background freshness under contention to protect UI resources; a stuck native query retains its slot. Additional tests prove manual refresh bypasses a fully occupied pool and a queued scan rechecks foreground busy state before reading. Focused controller + pool tests: 21 passed, zero failed. ## Phase 8 — conservative Source Control filesystem event routing

The native Source Control watcher previously classified paths only, allocating a Vec of path components for each worktree event and accepting read access plus other linked worktrees' private HEAD/index notifications observed by the main checkout's recursive watch. Ignore only known read/open/close read/execute access events, and exact foreign worktree administrative HEAD/HEAD.lock/index/index.lock files and reflog subtrees. Own private metadata takes precedence over its enclosing common directory. Preserve shared refs/config, structural and unknown administrative changes, mixed relevant rename paths, write and ambiguous access notifications. Rescan/empty path notifications bypass all filtering; errors still reach the inbox. Iterate path components without the Vec allocation. Keep existing generated-directory name exclusions unchanged rather than introduce a potentially stale ignored/tracked-path cache. This does not eliminate all redundant watcher events or make status scans incremental.

Correctness fix: retain Git info/exclude, info/attributes and sparse-checkout events (previously excluded as noisy info metadata); also register existing private/common info directories for linked worktrees outside the checkout, along with the existing refs watches. This does not add dynamic registration for later-created info directories or solve pre-existing scoped-workspace metadata coverage limitations. Preserve all bridge types, stream coalescing and phase 7 admission rules; no FRB regeneration needed.

Deterministic 5,103-event routing fixture (100 worktree names, 4,000 private administrative events, 1,000 reads, 100 real file edits, one shared ref event, one ignore-rule event and one rescan): old path-only rule would admit 5,101; new policy admitted 103, including both formerly lost correctness events. This is approximately 98% fewer admitted raw events in the simulated workload, not measured full status scan reduction, hardware utilization, or production UI latency. Actual Windows notify test used temporary linked metadata directories and observed index, shared info/exclude and shared refs events; classified the linked index event as relevant only to its owner (not the main checkout). Rust watcher-focused tests 10/10 passed. No new Dart or native API changes, Release measurements, or main merge.
